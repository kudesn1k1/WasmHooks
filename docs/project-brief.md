# Self-hosted платформа безопасного исполнения пользовательских расширений на WebAssembly

Рабочее название: **WasmHooks**. Описание для согласования темы и вилки сложности.

## Тема

Self-hosted платформа, которая позволяет SaaS-продукту безопасно исполнять кастомную логику своих клиентов в заранее определённых точках расширения. Клиенты пишут обработчики на любом языке, компилирующемся в WebAssembly, платформа исполняет их в изолированной песочнице со строгими лимитами и выдаёт результат продукту.

## Суть проекта простыми словами

Любой зрелый SaaS рано или поздно сталкивается с тем, что клиенты просят «немного своей логики»: посчитать скидку по собственным правилам, проверить заказ по внутреннему регламенту, обогатить данные. Реализовывать каждое пожелание силами команды продукта невозможно, а давать клиентам исполнять произвольный код внутри продукта опасно. Индустриальный ответ на эту проблему: продукт определяет точки расширения, клиент загружает скомпилированный WebAssembly-модуль, а специальная платформа исполняет его изолированно, с лимитами по памяти и времени и с доступом только к тем возможностям, которые продукт явно разрешил. Так устроены Shopify Functions, Cloudflare Workers и плагинные системы на базе Extism.

Мы делаем такую платформу как самостоятельный self-hosted продукт: SaaS разворачивает её у себя, описывает точки расширения и подключает через SDK. Готовый WebAssembly-рантайм мы берём с рынка, предмет проекта не рантайм, а инфраструктура вокруг него: мультитенантность, квоты, горизонтальное масштабирование исполнителей, отказоустойчивость, версионирование модулей, наблюдаемость.

## Роли

- **Оператор.** SaaS-продукт, развернувший платформу. Определяет точки расширения (хуки): имя, схемы входа и выхода, лимиты, разрешённые возможности.
- **Тенант.** Клиент оператора. Пишет, загружает и активирует обработчики на разрешённых хуках, видит свои логи и метрики.
- **Демо-оператор.** Для демонстрации мы реализуем небольшой интернет-магазин с хуками расчёта скидки и валидации заказа.

## Функциональные возможности (целевой объём на семестр)

- Реестр хуков оператора: схемы входа и выхода, лимиты времени и памяти, разрешённый набор host-функций.
- Загрузка WebAssembly-модулей тенантами, автоматическая валидация (соответствие хуку, проверка импортов против разрешённых возможностей, пробный запуск), версионирование, мгновенная активация и откат.
- Синхронные вызовы хуков из приложения оператора через SDK (Python и Go) с дедлайном, типизированными исходами и значением по умолчанию при отказе.
- Изолированное исполнение: лимит памяти и времени на вызов, отсутствие доступа к сети и файловой системе, только явно разрешённые host-функции.
- Квоты на тенанта: частота вызовов и параллельность, защита остальных тенантов от «шумного соседа», circuit breaker для сломанных обработчиков.
- Горизонтальное масштабирование исполнителей с маршрутизацией по consistent hashing, автоматическое перестроение при выходе узла из строя, повтор вызова на соседнем узле.
- Наблюдаемость: метрики и логи на тенанта, дашборд, playground для тестового вызова из консоли.
- Веб-консоли оператора и тенанта.
- Развёртывание в Kubernetes как self-hosted продукт, Docker Compose для разработки.

## Ограничения (осознанные, на этот семестр)

- Только синхронные хуки. Асинхронная модель (очереди, ретраи, DLQ) проектируется сейчас, реализуется в следующем семестре.
- Тенанты загружают уже скомпилированный WebAssembly. Сборка исходников на стороне платформы не входит в объём.
- Обработчики не совершают побочных эффектов изнутри исполнения: результат и желаемые эффекты возвращаются как данные, применяет их оператор. Это делает повтор вызова безопасным по построению.
- Квоты по времени исполнения (wall-clock), а не по числу инструкций: выбранный рантайм не поддерживает точный учёт CPU.
- Хранилище состояния для обработчиков (KV) и host-функции доступа к данным оператора не входят в объём семестра.
- Лимиты частоты вызовов считаются на каждой реплике шлюза приближённо, точный распределённый лимит в roadmap.

## Архитектурные акценты, которые мы обосновываем и демонстрируем

- **Разделение control plane и data plane.** Control plane (конфигурация, модули, версии) не участвует в обработке вызовов. Его недоступность не влияет на исполнение: исполнители работают по последнему известному снимку конфигурации.
- **Масштабирование.** Исполнители stateless относительно запросов, добавляются горизонтально. Consistent hashing даёт локальность тёплого кеша модулей. Нагрузочные тесты показывают зависимость латентности от числа исполнителей.
- **Отказоустойчивость.** Выход исполнителя из строя обнаруживается шлюзом, кольцо перестраивается, вызовы в полёте повторяются на соседе. Демонстрируется живым сценарием: под нагрузкой убивается pod исполнителя, магазин продолжает считать скидки.
- **Изоляция тенантов.** Лимиты памяти и времени на инстанс, bulkhead по параллельности, circuit breaker, ограниченные очереди и быстрый отказ при перегрузке.
- **Доказательная база.** ADR на каждое ключевое решение с отвергнутыми альтернативами, диаграммы C4 и sequence, нагрузочные сценарии на k6, тесты трёх уровней.

## Вилка сложности

1. **Гарантированный минимум.** Control plane с загрузкой, валидацией и активацией модулей; исполнитель с лимитами памяти и времени; Python SDK; демо-магазин с одним хуком; Docker Compose; ADR и диаграммы; нагрузочное измерение одной реплики.
2. **Целевой MVP.** Всё из минимума плюс: разделение шлюза и исполнителей, consistent hashing и discovery в Kubernetes, квоты и bulkhead на тенанта, circuit breaker, версионирование с откатом, консоли оператора и тенанта с playground и логами, Go SDK, второй язык обработчиков, нагрузочные сценарии масштабирования и отказа, живое демо с убийством узла.
3. **Следующий семестр.** Асинхронные хуки и джобы с очередью, ретраями и DLQ; исполнитель эффектов на стороне платформы с outbox; KV-хранилище тенанта; host-функции доступа к данным оператора и декларативное описание потребностей обработчика; распределённые лимиты; сборка модулей на стороне платформы.

## Команда

- Тимлид, backend (Go): шлюз, исполнитель, пул инстансов, Go SDK, нагрузочные тесты.
- Backend (Python): control plane, Python SDK, демо-магазин.
- Frontend: консоли оператора и тенанта.

## Стек

Go, Python (FastAPI), Extism поверх wazero (WebAssembly-рантайм на чистом Go), PostgreSQL, MinIO (S3-совместимое хранилище модулей), gRPC, Prometheus и Grafana, Kubernetes (kind/k3d), Docker Compose, k6. Обработчики для демо на Rust и TinyGo или JavaScript.
