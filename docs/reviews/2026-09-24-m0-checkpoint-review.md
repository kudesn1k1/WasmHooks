## Part A — core correctness

### Critical

#### C1. Compiled modules are shared across hooks: one hook's limits and allowlist apply to another hook's scripts
- **Where:** `internal/executor/executor.go:51-54` (`modKey{hash, defVersion}`), `:243` (cache lookup), `:255` (singleflight key `hash@defVersion`), `:289` (invalid-verdict cache); spec §8.1 line 356 has the same wording.
- **What is wrong:** `def_version` is a counter per hook. Every hook starts at 1. The compile cache key has no hook name, so two different hooks at the same `def_version` bound to the same module bytes get **one** compiled module. That module carries the `ModuleSpec` (memory pages, timeout, allowed host functions) of whichever hook compiled it first. The instance timeout (`runtime.go:164`, `m.spec.Timeout`) and the memory limit (`runtime.go:103`) both come from that spec. The ABI makes modules independent of the hook (D10: one `handle` export for every hook), and module storage is content-addressed, so the same hash bound to two hooks is a normal state, not an edge case.
- **Scenario (verified, E7):** hook `strict` (100 ms, 64 pages) and hook `lax` (2000 ms, 1024 pages), both `def_version: 1`. Tenant `y` binds `infinite-loop` to `lax` and tenant `x` binds the same bytes to `strict`. `y` calls first. Its compile is detached, so it finishes even though `y`'s caller gave up. Then `x` calls `strict` with a 1.5 s caller deadline. **Result: `outcome=timeout after 1.5s; compiles=1`.** `x`'s script ran 15× past its hook limit. With the default deadline (`timeout_ms + 100`) it would run 200 ms instead of 100 ms. With `deadline_ms: 30000` it runs up to `lax`'s 2 s. The memory limit follows the same path: `x`'s instances get 64 MiB instead of 4 MiB (same mechanism, not separately measured). The invalid verdict leaks too. If the module is invalid under one hook (for example it imports a host function that only the other hook allows), `invalid[(hash,1)]` returns `handler_error/invalid_module` to the other tenant, or the reverse: a module valid under the permissive hook runs under the strict one without being checked against it. In M0 no user host functions exist, so that escalation is latent. The limit violation is live.
- **Fix:** key the compile cache, the singleflight key and the invalid map by `(hash, hook name, def_version)`. Better still, key by a digest of everything that goes into `ModuleSpec` (`MemoryMaxPages`, `Timeout`, sorted `AllowedHostFunctions`): hooks with identical specs share a module, and hooks with different specs can never collide. Add an executor test with two hooks at `def_version 1` and one module (assert `compiles == 2` and that the strict timeout is honoured). Fix spec §8.1 to "(module_hash, hook, hook_def_version)", matching §7.3's "пара «хеш, определение хука»".

### Important

#### I1. A module that passes `CheckModule` but cannot be instantiated returns 503 `unavailable` on every call
- **Where:** `internal/sandbox/wasminfo/info.go:33-36` (lists function imports only), `internal/sandbox/check.go:32-46` (no signature checks), `internal/sandbox/extismrt/runtime.go:81-121` (never instantiates), `internal/executor/executor.go:170-177` (factory error → `unavailable/internal`).
- **What is wrong:** static validation sees only the **names** of **function** imports. It misses memory, table and global imports, and wrong signatures on allowed kernel names. wazero accepts such modules at compile time and rejects them at link time, which is `Instantiate`. The executor maps every factory error to `unavailable`, does not cache the verdict, and retries on every call.
- **Scenario (verified, E3):** hand-built modules pass `Compile` and fail `Instantiate`:
  - `(import "env" "memory" (memory 1))`: `module[env] not instantiated`. Toolchains built with `--import-memory` (C/Zig/Emscripten) produce exactly this.
  - `(import "extism:host/env" "alloc" (func (param i32) (result i32)))`: `signature mismatch: i32_i32 != i64_i64`.

  Each call is `HTTP 503, outcome unavailable` and gets retried. This is the "one tenant's bug becomes the platform's 5xx" failure that §6.1.3 argues against at length: retry middleware, 5xx alerts and outlier ejection all fire. `Preload` does not catch it either, because it only compiles. Spec §6.3 says the executor's own checks are the backstop for when the control plane skips validation, but this class gets through.
- **Fix:** at the end of `extismrt.Compile`, do one trial `cp.Instance(ctx, …)` and close it. Map a failure to `ErrInvalidModule`, which is then cached as `handler_error/invalid_module`. It costs one instantiate per compile (≈0.5 ms on Linux, next to ≈60 ms of compile). While there, also check that `handle` has type `() -> i32` (see M2) and reject any non-function import (`CompiledModule.ImportedMemories()` exists; the trial instantiate covers globals and tables). Defence in depth: instances of one compiled plugin share one wazero store under the names `main_N`, and a non-function import of `main_1` is not rejected statically. I checked that this cannot be exploited: wazero registers a module's name only after it instantiates successfully (`internal/wasm/store.go:328-337`), so `main_1` can never satisfy its own import. The trial instantiate closes the gap anyway.

#### I2. Platform failures inside `NewCompiledPlugin` are cached as "invalid module" and blamed on the tenant
- **Where:** `internal/sandbox/extismrt/runtime.go:107-110` wraps **every** `NewCompiledPlugin` error as `ErrInvalidModule`; `internal/executor/executor.go:288-290` caches `ErrInvalidModule` for the life of the process.
- **What is wrong:** by that point `wasminfo.Inspect` has already decoded and validated the module, so almost everything `NewCompiledPlugin` can still fail on is the platform's fault. The main case is `platform.MmapCodeSegment` failing: executable mmap refused by `MemoryDenyWriteExecute=yes` in a hardened systemd unit, SELinux `execmem`, or commit-limit exhaustion. The one module-caused failure left is "memory min exceeds the hook's max pages", and only because `Inspect` runs without the limit.
- **Scenario A (verified, E9): operator configuration blamed on tenants.** The Extism kernel's own memory has `min = 16` pages (E8), and `WithMemoryLimitPages` applies to every module in the plugin's runtime. A hook with `memory_max_pages: 8`, which `config.validate` accepts because it only checks `> 0` (`config.go:134-136`), fails the **kernel** compile: `sandbox: module violates spec: instantiating extism module: section memory: min 16 pages (1 Mi) over limit of 8 pages`. Every binding on that hook becomes a cached `200 handler_error/invalid_module`. A limit of 16 fails on the guest instead (`min 17 pages`, which is a legitimate "module too big for this hook"). Also require `memory_max_pages ≥ 16` in `config.validate`, or better, the kernel's minimum plus the guest's.
- **Scenario B (by source reading, not reproduced; reproducing needs an mmap failure):** the operator deploys under a unit with `MemoryDenyWriteExecute=yes`. Every compile fails with an mmap error, every binding is cached as invalid, and every call returns `200 handler_error/invalid_module`. The tenants are blamed, the operator's 5xx alerting stays quiet, and the state survives the config being fixed until the process restarts. Cancellation cannot poison the cache (the compile is detached, which is correct), but failures can.
- **Fix:** run `Inspect` with `WithMemoryLimitPages(spec.MemoryMaxPages)` so the only module-caused error is caught statically. Then wrap `NewCompiledPlugin` errors as a plain internal error, which maps to `unavailable` and is not cached. Optionally compile a tiny module at startup so a broken host fails fast, before `/readyz` reports ready.

#### I3. A client disconnect or a short caller budget is recorded as the tenant's `timeout`, with no reason
- **Where:** `internal/gateway/httpapi/httpapi.go:115` (`r.Context()`), `internal/gateway/gateway.go:117`, `internal/sandbox/extismrt/runtime.go:218-221` (`ExitCodeContextCanceled` or any `callCtx.Err()` → `ErrTimeout`), `internal/executor/executor.go:215-216` (`timeout`, reason `""`).
- **What is wrong:** spec §9.1 step 4 intentionally stops the script at `min(request deadline, hook timeout)`, so killing it at the caller's deadline follows the spec. But the outcome is `timeout` with an empty reason in both cases, and a client **disconnect** (context `Canceled`, not `DeadlineExceeded`) also comes out as `timeout`. The OpenAPI text defines `timeout` as "скрипт запускался, но не уложился в лимит времени хука", which is not what happens in either case.
- **Scenario (verified, E4):** a hook with a 1 s limit, and the operator's HTTP client disconnects after 20 ms. Result: `ErrTimeout: module closed with context canceled`, and the invocation record says the tenant's script timed out. The same happens with `deadline_ms: 20` on a 50 ms hook. The per-tenant timeout rate that the consoles and the MVP circuit breaker will read counts the operator's behaviour against the tenant.
- **Fix:** in `classify` or the executor, look at the parent context first. If it was `Canceled`, return `unavailable` with reason `caller_canceled` (or keep the script running under `context.WithoutCancel` plus the deadline; AWS Lambda lets a synchronous invoke finish after the client goes away). If the effective deadline was the caller's and not the hook's, keep `timeout` but set reason `caller_deadline`. Align the OpenAPI wording with §9.1. The related minor case, a pool wait ended by the context being reported as `pool_saturated`, is M4.

#### I4. Shutdown race: a detached compile after `Runtime.Close` panics and crashes the process
- **Where:** `internal/sandbox/extismrt/runtime.go:81-121` (checks `r.closed` only **after** `NewCompiledPlugin` has used the shared cache), `internal/executor/executor.go:255-259` (the detached singleflight compile outlives the request), `:341-353` (`Close` does not wait for in-flight compiles), `cmd/dataplane/main.go:155` (`exec.Close`, then `rt.Close`).
- **What is wrong:** `wazero.CompilationCache.Close` calls `engine.Close`, which sets `compiledModules = nil`. A compile that runs afterwards writes to that nil map.
- **Scenario (verified, E6):** compile once, `rt.Close`, then compile new bytes: `panic: assignment to entry in nil map`. In production, SIGTERM arrives while `Preload` is running or just after a request timed out waiting for a compile. `srv.Shutdown` returns because handlers have exited, but the detached singleflight goroutine is still compiling. `rt.Close` then closes the cache and the compile panics. `singleflight.DoChan` re-panics in a fresh goroutine (`golang.org/x/sync@v0.23.0/singleflight/singleflight.go:166-168`, `go panic(e); select {}`) so it cannot be recovered, and the process crashes instead of shutting down gracefully. The blast radius is shutdown only, but it is a crash, and `cmd/demo` stops the binary.
- **Fix:** in `extismrt.Runtime`, have compiles hold an `RLock` (or an in-flight `WaitGroup`) and have `Close` take the write lock, checking `closed` **before** `NewCompiledPlugin`. `Executor.Close` should also wait for in-flight compiles, or let them fail cleanly on `ErrClosed`.

#### I5. `module.Close` does not free machine code, and the shared compilation cache it depends on buys almost nothing
- **Where:** `internal/sandbox/extismrt/runtime.go:74-76, 93-96` (shared `CompilationCache`), `:171-180` (`module.Close` → `CompiledPlugin.Close`); go-sdk `plugin.go:306-308` (`CompiledPlugin.Close` only closes the wazero runtime); wazero `runtime.go:392-397` (the engine is closed only when there is no cache), `config.go:381-383` (only `CompiledModule.Close` decrements the refcount, and Extism never calls it). Spec §7.3 line 343.
- **What is wrong:** with a shared cache, each compiled module's machine code (mmap'd, outside the Go heap) stays alive until `Runtime.Close` (process exit), whatever happens to the module. §7.3's reason for the cache ("so the Extism kernel is not recompiled per module") is weak: `extism-runtime.wasm` is 3,474 bytes.
- **Evidence (E1, repeated 3×):** compiling distinct bytes with a warm kernel takes 57–86 ms/op; with no shared cache, 57–62 ms/op, the same within noise. Compiling module X, `Close`, then compiling X again takes **7–10 ms**, a cache hit, which proves the code survived `Close`. Harmless in M0 (no eviction), but the MVP LRU (§9.1 "LRU с лимитом добавляется в MVP") would evict modules and free nothing.
- **Fix:** drop the shared cache, i.e. make `DisableSharedCompilationCache` the default. `runtime.Close` then closes the engine and the code is freed. The only cost is that recompiling identical bytes, for example the same hash under a new `def_version`, goes from ≈9 ms to ≈60 ms. If the cache stays, document that eviction frees no code and use a per-cache generation that is closed as a whole. Update ADR 0003/§7.3. Interaction with C1: without the cache, the C1 fix multiplies full compiles by the number of distinct specs per hash, and a hook `def_version` bump recompiles every binding at ≈60 ms. Keying by **spec digest** rather than `(hash, hook, def_version)` is what keeps that cheap: a new `def_version` that does not change the spec reuses the compiled module.

#### I6. The pool's OOM guarantee in spec §8.2 is off by up to about 3.4× during memory growth
- **Where:** spec §8.2 line 375 ("в худшем случае память равна `global_max × memory_max_pages × 64 КиБ` плюс накладные расходы"); `internal/sandbox/extismrt/runtime.go:93-107` (default `RuntimeConfig`); wazero `internal/wasm/memory.go:263-268` (`Grow` does `append(m.Buffer, make([]byte, delta)...)`, so it reallocates with Go's ≈1.25× growth, copies, and leaves the old buffer as garbage).
- **Evidence (E2):** peak `HeapInuse` above baseline while one `memory-bomb` instance runs to its trap:

  | limit | peak heap | × limit |
  |---|---|---|
  | 64 pages (4 MiB) | 6.0 MiB | 1.50× |
  | 256 pages (16 MiB) | 46.6 MiB | 2.91× |
  | 1024 pages (64 MiB) | 217.7 MiB | 3.40× |

  Heap in use right after the trap at 64 MiB is still 132 MiB.
- **Scenario:** `global_max 256` with a 256-page hook gives a nominal 4 GiB, but real transient peaks can reach ≈12–14 GiB if many tenants grow memory at once. The count cap does not deliver the promised OOM protection.
- **Second factor (by source reading, not measured):** each instance has **two** limited linear memories, the guest's and the Extism kernel's (`min 16` pages, E8). `WithMemoryLimitPages` caps each one separately, and a guest can grow the kernel memory through the allowed `alloc` import. The per-instance bound is therefore ≈2 × `memory_max_pages` × 64 KiB before the growth factor.
- **Fix:** size `global_max` from a memory budget: `global_max ≤ budget / (k × max_pages × 64 KiB)`, with k≈3 until growth is fixed. Better, make the cap memory-denominated: a weighted semaphore that acquires `max_pages` units per instance, so a 1024-page hook consumes 16× more of the budget than a 64-page one. Set `GOMEMLIMIT` to roughly 85% of the container limit as a backstop. Evaluate `RuntimeConfig.WithMemoryCapacityFromMax(true)` (no reallocation or copy, but it reserves `max` per instance: an untouched `make` costs virtual memory on Linux, but Go counts the full capacity as heap for GC pacing; RSS effect **Unverified**) or a custom mmap allocator via `experimental.WithMemoryAllocator(ctx, …)` passed through `Instance(ctx)`. The latter reserves `max` virtually, commits on grow, never copies and is invisible to the GC.

#### I7. CPU-bound scripts at or above GOMAXPROCS break timeout precision and the "A unaffected by a hung B" property
- **Where:** `internal/pool/pool.go` (the global cap bounds instances, meaning memory, not the number of scripts executing at once, which is what consumes CPU); spec §2 DoD item "merchant-a параллельно с зависшим merchant-b … латентность в пределах нормы"; `TestExecutorTimeoutDoesNotBlockOtherTenant` runs only one hung script.
- **Evidence (E5, Windows, GOMAXPROCS=16, 50 ms limit):**

  | concurrent infinite loops | overshoot p50 | overshoot max | neighbour's warm call |
  |---|---|---|---|
  | 16 | 13.6 ms | 16.6 ms | below clock resolution |
  | 32 | 4.2 ms | 26.9 ms | 1.6 ms |
  | 64 | 4.5 ms | 37.5 ms | **14.4 ms** (≈50× its idle 0.3 ms) |

  Mechanism: wasm native code cannot be interrupted by Go's asynchronous preemption (wazero RATIONALE.md, "Why it's safe to execute runtime-generated machine codes…"). Timers need a free P (a Go scheduler processor), so the watchdog runs only once sysmon (the Go runtime's monitor thread) forces preemption, about every 10 ms, at wazero's `FailIfClosed` Go callbacks. With `global_max 256` and a default per-key limit of 4, four malicious tenants saturate a 16-thread box.
- **Fix:** admission control is out of M0 scope, so for M0 record it in `spike-results.md` and in the DoD demo caveat. Plan for MVP a process-wide semaphore on **running** calls of about GOMAXPROCS×k, separate from the instance cap, plus a Linux run of the saturation case (see S7 below).

### Minor

- **M1. A non-zero `rc` without an error message counts as success.** `extismrt/runtime.go:199` discards `rc`, and go-sdk `extism.go` returns `(rc, output, nil)` when `rc != 0` and no error was set. E3: `handle` returning `1` gives `out="" err=nil`, which becomes `handler_error/invalid_output` with the instance put back as healthy. It should be `ErrGuest` with instance closed. Fix: `if rc != 0 && err == nil { err = fmt.Errorf("%w: exit code %d", sandbox.ErrGuest, rc) }`.
- **M2. `handle`'s signature is not checked.** `sandbox/check.go:34`. E3: `handle(i32) -> i32` compiles, then every call returns `ErrGuest: expected 1 params, but passed 0` and the instance is recycled every time. It should be `ErrInvalidModule` at compile. Fix: require `() -> i32` (or `() -> ()`) via `ExportedFunctions()[Export].ParamTypes()/ResultTypes()`.
- **M3. Double compile race.** `executor.go:243-259`: the cache check happens under `e.mu`, and `DoChan` runs after unlock. If a flight for the same key finishes in between, a second flight compiles again, and `:297` overwrites `e.modules[key]` without closing the previous module. That module leaks until `Runtime.Close` and breaks "compile once". By code reading; not reproduced. Fix: re-check `e.modules` and `e.invalid` inside the singleflight function.
- **M4. `pool_saturated` when the caller's context ended the wait.** `pool.go:164-165` → `executor.go:174-175`. The ledger's ruling ("T6 test 6 asserts ErrSaturated") keeps the outcome right (`unavailable`), but the reason cannot tell "tenant at its concurrency limit" from "caller budget exhausted". Suggest `fmt.Errorf("%w: %w", ErrSaturated, ctx.Err())` so the executor can choose `deadline_before_start` without changing the contract. The same goes for a factory error caused by the deadline (`executor.go:176-177`, reported as `internal`).
- **M5. `Release` is not deferred.** `executor.go:170-194`. A panic between `Acquire` and `Release`, which `net/http` recovers per request, would leak the pool slot permanently: after `limit` leaks the tenant is saturated for good. Nothing in the current code path is known to panic. Fix: `defer func(){ if !released { lease.Release(false) } }()`.
- **M6. `Preload` is sequential.** `executor.go:315-332`. At ≈60 ms per distinct module on Linux, 100 modules delay `/readyz` by ≈6 s and 1,000 by ≈1 min. Fix: bounded parallelism (errgroup with GOMAXPROCS workers); compile is CPU-bound and single-threaded per module.
- **M7. `wasminfo.Inspect` costs 5–8 ms per compile.** `wasminfo/info.go:23-26`: the interpreter "compile" translates every function. That is ≈65–70% of a cache-hit compile (E1). It does not matter on a real cold miss (≈60 ms), but it inflates S1. Optional: walk the import and export sections directly. `github.com/tetratelabs/wabin` is already in `go.sum`.
- **M8. `CompileTimeout` has no effect.** `executor.go:46-48, 256`: neither `modstore.FS.Get` nor the wazero compile honours the context, so a stuck fetch or compile cannot be bounded. Either document it or drop the option until an HTTP or S3 modstore needs it.
- **M9. `deadline_ms` above 30000 is clamped, but the contract says `maximum: 30000`.** `httpapi.go:112` (clamp, asserted by `TestDeadlineClamped`) vs `api/invoke.openapi.yaml:326-330`. A strict client or validator reads the schema as "400 above 30000". Pick one and state it in the contract.
- **M10. `module_hash` appears when the script did not run.** `gateway.go:144-147` sets it for every `handler_error`, including `invalid_module`, where the script never ran, while the contract says "Присутствует, если скрипт запускался". Either set it only when `Reason != invalid_module`, or change the wording to "если модуль был определён".
- **M11. `duration_ms` misses part of the request.** `gateway.go:90` starts the clock after authentication, body read and JSON parse, while the contract says "время от получения запроса". Take the start time in `httpapi.invoke`.
- **M12. No body read deadline.** `main.go:120-124` sets only `ReadHeaderTimeout`, so a slow-body client holds a connection indefinitely. Add `ReadTimeout`, for example 10 s, since bodies are ≤ 1 MiB.
- **M13. Shutdown vs long hooks.** `main.go:151` gives 10 s, but `config.go:131-136` has no upper bound on `timeout_ms` or `memory_max_pages`. Calls still running at shutdown have their runtime closed under them: exit code 0, then Extism's "failed to get output: module closed with exit_code(0)", then `classify` returns `ErrGuest`, and the tenant is blamed for a shutdown. Bound `timeout_ms` (for example ≤ 30000) and `memory_max_pages` in snapshot validation, and set the shutdown timeout to at least the maximum `timeout_ms` plus a margin.
- **M14. One oversized log line drops the rest.** `logbuf.go:25-28`: a single message over 16 KiB sets `truncated`, and every later line in the call is dropped. The marker also makes `maxLines + 1` lines. Consider truncating the long message itself and counting the marker inside the cap.
- **M15. Hot path takes the executor mutex and §9.2 tests are incomplete.** `executor.go:228-236` takes `e.mu` and writes `e.hooks` on every `Execute`, sharing the lock with the compile cache. It is uncontended today; in MVP use an atomic snapshot keyed by view. Separately, §13 says "Все строки таблицы 9.2 покрываются тестами", but no executor test covers "`Instantiate` error → `unavailable`" (reachable, see I1) or "`ErrClosed` during call".

### Checked and found sound (not findings)
- **Tenant isolation:**
  - Instances are never shared across keys, and the key includes the tenant.
  - Config is `maps.Clone`d and **assigned** (`runtime.go:157-161`); Extism only reads `plugin.Config` in `configGet`.
  - Log buffers and the `Var` store are per instance and reset per call. Guest memory is per instance (`main_N`).
  - The only shared state is the compiled plugin, the wazero store and the process-wide log level, which is fine apart from C1.
- **Pool:**
  - Every `Acquire` success is paired with exactly one `Release`, protected by `sync.Once`.
  - `total` counts instances idle, leased and being created. It stays consistent across evict and retry, factory failure, reap, `Close` and release after `Close`.
  - The `changed` channel is captured under the lock before waiting, so there is no lost wakeup.
  - Factory and `Close` calls run outside the lock, so there is no deadlock with the reaper (`Close` releases `m.mu` before `reaperWG.Wait`).
  - After `Close`, leased instances are closed on release.
- **Timeout boundary:** `ctx.Err()` is checked after `Acquire` and before `Call` (`executor.go:180-183`), so a script that never started never reports `timeout`. A call with an already-expired context is also caught by wazero's entry check (`call_engine.go:256-263`). The Extism post-call kernel calls use the call context, so a module the watchdog closed at the deadline surfaces as an error and is never released as healthy.
- **HTTP:** 401 before the body is read, 413 via `MaxBytesReader`, 400 variants, 503 for not ready or a broken schema, the `X-Hook-Outcome` header, `error` null for `timeout`, empty `effects` unless `ok`. All match §6.1.3.

## Part B — spike harness validity (checkpoint 1)

The Linux files (`*-linux-wazero-1.12.txt`, AMD EPYC 7763, 4 vCPU, Go 1.26.0, committed in 991bb6e after f4fb736) are the primary source for anything that needs Linux.

| # | Verdict | Why |
|---|---|---|
| S1 `BenchmarkCompile` | **flawed** | `sharedCache=true` recompiles **identical bytes**. Extism never closes its `CompiledModule`s, so `m.Close` evicts nothing, and every iteration after the first is a full cache hit on kernel **and** module. It measures `Inspect` (5–8 ms) plus decode/validate (≈2–3 ms), not "kernel cached, module compiled". The real cold miss for a new module is ≈ `sharedCache=false`: E1 57–86 vs 57–62 ms Windows; S6 Linux 58–65 ms vs S1-false 64–71 ms. The kernel is 3.5 KB, so its cache effect cannot be measured. Spec S1 asks for "стоимость холодного промаха, эффект общего кеша", and the benchmark overstates the effect about 7×. Add a `distinctBytes` case (`withCustomSection(i)` per iteration) and report `Inspect` separately. |
| S2 `BenchmarkInstantiate` | **valid but not the cold-start cost** | It measures `Instantiate` plus `Close`. The first call on a fresh instance costs far more than a warm call (the guest grows its memory, about 1.4 MB extra allocated per op), so the cold penalty is **S4 − S3**: Linux ≈1.75 − 0.24 ≈ **1.5 ms**, Windows ≈1.45 − 0.30 ≈ 1.15 ms, against S2 Linux 0.47–0.59 ms. On Windows S2 (1.4–1.9 ms) is *greater than* S4 (1.3–1.6 ms), which is impossible if both measured the same work. Allocation and GC noise dominates at ≈2.2 MB/op garbage, so use Linux. |
| S3 `BenchmarkCallWarm` | **valid** | Linux 232–263 µs, 504 KB/op, 277 allocs/op. See controller observation (1) below. Use `CallWarmParallel` for capacity: Linux ≈80 µs/op on 4 vCPU ≈ 12.5k calls/s per 4 vCPU. The single-goroutine loop keeps ≈1.75 cores busy (profile: 6.53 s CPU in 3.74 s wall) because of GC and scheduler work. Windows `-16` and Linux `-4` parallel numbers cannot be compared. |
| S4 `BenchmarkCallCold` | **valid** | Linux 1.67–1.92 ms, Windows 1.33–1.59 ms. This is what a pool miss costs. |

### Controller's observations, checked

1. **Warm call ≈300–500 µs with ≈488 KiB/op, from go-sdk calling `ExportedFunction` per kernel call: correct, and it is not the whole story.**
   - Source: go-sdk `host.go:256-276` (`extismFunc` does `extism.ExportedFunction(name)` on every invocation), `extism.go` `SetInputWithContext`/`GetOutputWithContext`/`GetErrorWithContext` do the same, and wazevo `NewFunction` → `callEngine.init` makes a 10 KiB stack each time (`call_engine.go:143-158`, `module_engine.go:200-224`).
   - My profile (scratch, Windows): **97.7% of allocated bytes** come from `moduleEngine.NewFunction`/`callEngine.init`, ≈40–50 call engines per call (≈11.8 KB each against 504 KB/op).
   - **Second cost the controller did not mention:** every one of those kernel calls runs with the call's cancellable context. With `CloseOnContextDone` enabled, wazero starts a watchdog goroutine per call (`module_instance.go:32-40`). The CPU profile shows `newproc`, `wakep`, `semasleep`/`semawakeup`, `lock2` and `findRunnable` at ≈15–20% of samples and GC mark and sweep at ≈16–25%.
   - Both costs sit inside go-sdk and can only be fixed in a fork: cache the kernel `api.Function`s per `Plugin` and call kernel exports with a context that has no `Done` channel, since the outer `handle` call's watchdog already covers termination. Given D7 (go-sdk unmaintained since May 2025) a small fork is defensible; record it in ADR 0003. Estimated gain: most of the 500 KB/op and a large share of CPU (**Unverified**; measure after the fork).
   - Linux warm is 232–263 µs; the "300–500 µs" range is Windows.
2. **Windows monotonic clock is tick-quantised: correct.** Go's `nanotime` on windows/amd64 reads `KUSER_SHARED_DATA._INTERRUPT_TIME` (`GOROOT/src/runtime/time_windows.h:13`, `time_windows_amd64.s:12`), which is updated per clock interrupt. A p50 of exactly `0s` over 2,000 samples is only possible with a quantised clock, and Linux confirms p50 125–137 µs. Benchmark `ns/op` values stay valid on Windows because they are averaged over ≥1 s; per-sample percentiles are not. The product's own `duration_ms`/`exec` on Windows are quantised too.
3. **Time-to-OOM "grows superlinearly" with the limit: not supported.**
   - Data: Linux 1.0 / 20 / 50 ms and Windows 1.6 / 18 / 78 ms for 4 / 16 / 64 MiB, i.e. per MiB 0.25 / 1.25 / 0.78 ms (Linux) and 0.41 / 1.15 / 1.22 ms (Windows). That is a jump between 4 and 16 MiB, then roughly linear (Windows) or sub-linear (Linux).
   - Mechanism: wazero grows memory with Go `append` (geometric, ≈1.25×, `memory.go:267`), so copying amortises to linear, not quadratic.
   - The 4 MiB point is dominated by the fixed ≈1.06 MiB of initial memory: only ≈2 of the bomb's 1 MiB chunks fit.
   - The copying is real, though. It is what drives the 3× heap peak (I6).
   - What matters is unchanged: a memory bomb burns ≈1–1.5 ms of CPU per MiB of limit, so whether it ends as `handler_error` or `timeout` depends on the ratio `memory_max_pages / timeout_ms`. With 1024 pages and a 50 ms timeout it will usually be `timeout`. The ledger ruling (64 pages for demo and test hooks) is right; write the ratio rule into `spike-results.md`.

### What the numbers imply

- **`global_max` 256:** at 2.1–2.4 MiB per small-script instance that is ≈540–615 MiB of live heap, and up to ≈1.2 GiB RSS with GC headroom. That is fine for small scripts. The bound, however, is set by `memory_max_pages`: 256 × 16 MiB × ~3 (transient) ≈ 12 GiB for 256-page hooks. Derive the cap from a memory budget, or better make it memory-weighted (I6), and add `GOMEMLIMIT`. `global_max` bounds memory, not CPU; the tail-latency bound needs a separate cap on running calls (I7).
- **Warm pool:** keep the pool's reuse. A cold call costs ≈6× a warm one (Linux 1.5 ms vs 0.24 ms), which is worth it for throughput. **Creating instances ahead of demand** (pre-warming, out of M0 scope) would save at most ≈1.5 ms on the first call per key. Against hook timeouts of tens of ms it is not justified until an SLO below ≈2 ms p99 appears. The §16 risk "Инстанцирование дорогое (единицы мс и выше)" is **not triggered** on Linux (0.5 ms instantiate, 1.5 ms cold penalty).
- **Preload:** a real per-distinct-module compile is ≈58–65 ms on Linux (not 85–90 ms; that is the Windows no-cache S1 figure). An identical-bytes recompile is ≈9–12 ms with the shared cache. Preload is justified; parallelise it (M6). A compile that is not preloaded still fits the default deadline (`timeout_ms + 100`) most of the time, and because the compile is detached, the next call succeeds even if the first one fails. Once C1 is fixed, the number of compiles is the number of distinct `(hash, hook, def)` triples, not distinct hashes; budget Preload accordingly.

## Keep as is (good decisions, do not change)
1. The pool design: per-key LIFO idle list, broadcast via a closed-and-replaced channel captured under the lock, factory outside the lock, `Lease` with `sync.Once`, eviction of the oldest idle instance across keys under the global cap, no explicit invalidation (a new key per config, script or definition change).
2. `Release(true)` on bad output and `Release(false)` on any `Call` error, with output parsing done after the instance is released.
3. The "deadline before start" check after `Acquire`, together with `unavailable` for anything before the script starts. The `timeout`/`unavailable` boundary is clean in code (I3 is about attribution, not the boundary).
4. A detached singleflight compile that caches `invalid_module` and never caches fetch errors (after I2, never caches platform errors either).
5. The Extism hardening: `Timeout > 0` enforced, `MaxVarBytes` set, `AllowedHosts` empty, HTTP denied statically, config assigned and never mutated, the log level set explicitly, and log buffers capped per call.
6. `execproto` as a pure-data contract, the gateway pinning versions, a `stale_config` path in place from day one, and `archtest` as a fitness function.
7. The HTTP contract: 200 for `timeout`/`handler_error` with `X-Hook-Outcome` (the Lambda precedent is well argued), problem+json, constant-time auth over SHA-256, 413 via `MaxBytesReader`.
8. modstore: the hash format regex blocks path traversal, and content is verified after the read.
9. The contract suite `sandboxtest` and the isolation tests (counter and echo-config across tenants on the same module). Extend them with the C1 two-hook case and the I1 link-failure case.
