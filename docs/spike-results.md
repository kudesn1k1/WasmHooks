# Спайк рантайма: результаты

Milestone 0, 2026-09-24. Вопросы спайка — спек M0 §12 и основной спек §16. Сырые данные — `docs/spike/raw/`, код измерений — `dataplane/internal/sandbox/extismrt/{bench,spike}_test.go` и `dataplane/cmd/dataplane/spike_test.go`. Методику и выводы проверил независимый ревьюер, отчёт — `docs/reviews/2026-09-24-m0-checkpoint-review.md`; поправки ревью уже внесены ниже.

## Как воспроизвести

```bash
cd dataplane
# S1–S4, S9: бенчмарки
go test -run '^$' -bench . -benchmem -count 10 ./internal/sandbox/extismrt/ ./internal/schema/
# S5–S8, S7b, S11: измерения
go test -count=1 -run Spike -v ./internal/sandbox/extismrt/ -args -spike
# S12: сквозная задержка через бинарник
go test -count=1 -run Spike -v ./cmd/dataplane/ -args -spike
```

На Linux то же самое запускает workflow `.github/workflows/bench.yml` и выкладывает артефакт `spike-linux`.

## Машины

| | Windows (разработка) | Linux (эталон) |
|---|---|---|
| CPU | Intel Core i5-1240P, 16 потоков | AMD EPYC 9V74, 4 vCPU (GitHub Actions `ubuntu-latest`; модель CPU раннера меняется от прогона к прогону) |
| ОС | Windows 11 Pro 10.0.26100 | Ubuntu, ядро 6.17 (Azure) |
| Go | 1.26.4 | 1.26.0 |
| wazero | 1.9.0 и 1.12.0 | 1.12.0 |
| Extism go-sdk | 1.7.1 | 1.7.1 |

**Методическая оговорка.** Сырые данные Windows по S7b и S12 — `docs/spike/raw/measure-windows-s7b-s12.txt`, два прогона; остальные — `*-windows-*.txt`. В Windows монотонные часы Go обновляются по тику системного таймера, поэтому длительности отдельных вызовов короче миллисекунды квантуются (отсюда `p50=0s` в сырых данных Windows). Средние значения бенчмарков это не затрагивает: они считаются по тысячам итераций. **Перцентили задержки отдельных вызовов берутся только с Linux.** Общие раннеры CI шумные: разброс между прогонами до 15%.

## Горячая точка аллокаций

Тёплый вызов выделяет ~490 КиБ, поэтому p99 в 3–4 раза выше p50 (паузы GC). По профилю, 85–98% байтов выделяет `wazevo.(*callEngine).init`: go-sdk Extism на каждом вызове заново получает функции ядра через `ExportedFunction` (`alloc`, `length`, `input_*`, `output_*`, `error_get`, `reset`), и wazero каждый раз создаёт новый call engine со стеком около 10 КиБ — 40–50 штук на вызов. Вторая цена, найденная ревьюером: все эти вызовы ядра идут с отменяемым контекстом, и на каждый wazero запускает горутину-наблюдателя. Это 15–20% CPU в профиле плюс ещё 16–25% на GC.

Обе проблемы внутри go-sdk. Исправление — закешировать функции ядра на инстанс и вызывать их с контекстом без отмены (прекращение уже покрывает наблюдатель внешнего вызова `handle`). go-sdk не обновлялся с мая 2025, поэтому это небольшой форк; контрактный набор `sandboxtest` проверит, что форк ведёт себя так же (ADR 0003).

## Целевой SLO data plane

Для тёплого вызова тривиального скрипта на эталонной машине (Linux, 4 vCPU), при параллельности не выше числа ядер:

- **накладные расходы платформы p99 ≤ 3 мс, p50 ≤ 0.5 мс** — включая HTTP, аутентификацию, обе проверки схем, пул и Extism;
- время исполнения самого скрипта — сверх этого и ограничено `timeout_ms` хука.

Текущая реализация укладывается: p99 0.88 мс последовательно и 2.3 мс при 4 клиентах (S12). Запас нужен, потому что общие раннеры CI шумные. После форка go-sdk цель MVP — p99 ≤ 1 мс при 4 клиентах.

SLO не покрывает:

- **холодный путь** — первый вызов тенанта после старта или переезда стоит ~1.4 мс сверх тёплого, компиляция вынесена в предзагрузку;
- **насыщение CPU** — пока число исполняемых вызовов не ограничено, точность таймаутов и латентность соседей при крутящихся скриптах не гарантированы (S7b).

## Задачи MVP, которые вытекают из спайка

1. **Ограничение одновременно исполняемых вызовов** (≈ число ядер, отдельно от лимита инстансов) — S7b.
2. **Форк go-sdk Extism** с кешем функций ядра и контекстом без отмены — горячая точка аллокаций.
3. **Лимит инстансов, взвешенный по `memory_max_pages`**, и `GOMEMLIMIT` для процесса — S5, S8, ревью I6.
4. **Замер RSS** на инстанс (с выросшей памятью) и на скомпилированный модуль — прежде чем задавать размер LRU.
5. **Выбор второго языка скриптов** (TinyGo или JS): фикстуры на обоих и прогон того же спайка — в M0 не измерялось.
6. **Разбор модуля без компиляции интерпретатором** (прямой проход по секциям): 5–8 мс на каждую компиляцию — ревью M7.
