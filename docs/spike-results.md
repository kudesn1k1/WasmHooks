# Спайк рантайма: результаты

Milestone 0, 2026-09-24. Вопросы спайка — спек M0 §12 и основной спек §16. Сырые данные — `docs/spike/raw/`, код измерений — `dataplane/internal/sandbox/extismrt/{bench,spike}_test.go` и `dataplane/cmd/dataplane/spike_test.go`.

## Как воспроизвести

```bash
cd dataplane
# S1–S4, S9: бенчмарки
go test -run '^$' -bench . -benchmem -count 10 ./internal/sandbox/extismrt/ ./internal/schema/
# S5–S8, S11: измерения
go test -count=1 -run Spike -v ./internal/sandbox/extismrt/ -args -spike
# S12: сквозная задержка через бинарник
go test -count=1 -run Spike -v ./cmd/dataplane/ -args -spike
```

На Linux то же самое запускает workflow `.github/workflows/bench.yml` и выкладывает артефакт `spike-linux`.

## Машины

| | Windows (разработка) | Linux (эталон) |
|---|---|---|
| CPU | Intel Core i5-1240P, 16 потоков | AMD EPYC 7763, 4 vCPU (GitHub Actions `ubuntu-latest`) |
| ОС | Windows 11 Pro 10.0.26100 | Ubuntu, ядро 6.17 (Azure) |
| Go | 1.26.4 | 1.26.0 |
| wazero | 1.9.0 и 1.12.0 | 1.12.0 |
| Extism go-sdk | 1.7.1 | 1.7.1 |

**Методическая оговорка.** В Windows монотонные часы Go обновляются по тику системного таймера, поэтому длительности отдельных вызовов короче миллисекунды квантуются (отсюда `p50=0s` в сырых данных S6 Windows). Средние значения бенчмарков это не затрагивает: они считаются по тысячам итераций. **Перцентили задержки отдельных вызовов берутся только с Linux.**

## Горячая точка аллокаций

Тёплый вызов выделяет ~490 КиБ и 277 объектов, из-за чего p99 в 3–4 раза выше p50 (паузы GC). Профилирование (`pprof`, alloc_space) показывает, что 85% байтов выделяет `wazevo.(*callEngine).init`: go-sdk Extism на каждом вызове заново получает функции ядра через `ExportedFunction` (`alloc`, `length`, `input_*`, `output_*`, `error_get`, `reset`), и wazero каждый раз создаёт новый call engine со своим стеком. Ещё ~12 МБ из 830 МБ за прогон — горутина наблюдения за контекстом на каждый вызов (`CloseModuleOnCanceledOrTimeout`).

Исправление известно: закешировать `api.Function` ядра один раз на инстанс. Это ~20 строк в go-sdk, но go-sdk не обновлялся с мая 2025, так что исправление означает форк. Находка усиливает риск из ADR 0003 и превращает его в конкретную задачу MVP: форк go-sdk с кешем функций ядра, цель — снизить аллокации на вызов на порядок и сблизить p99 с p50. Контрактный набор `sandboxtest` проверит, что форк ведёт себя так же.

## Решения по итогам

| Параметр | Было в спеке | Решение | Обоснование |
|---|---|---|---|
| Версия wazero | 1.9 (закреплена go-sdk) | **1.12** | S10 |
| Тёплый пул | предположение | **нужен** | S2, S4: холодный вызов в 5–7 раз дороже тёплого |
| Preload модулей | предположение | **нужен** | S1: 60–90 мс на модуль, дедлайн запроса по умолчанию 150 мс |
| `global_max` | 256 | **256 по умолчанию, в продакшене считать от бюджета памяти** | Инстанс стоит `2.4 МиБ + memory_max_pages × 64 КиБ` в худшем случае. При хуке на 64 страницы (4 МиБ): ~6.4 МиБ × 256 ≈ 1.6 ГиБ. Формула: `global_max ≤ бюджет / (2.4 МиБ + memory_max_pages × 64 КиБ)` |
| `memory_max_pages` у хуков | 256 в примерах | **задавать по потребности, 64 для демо** | S8: большие лимиты удлиняют жизнь бомбы; `discount` хватает ~1 МиБ |
| Проверка входа по схеме (D5) | решено | **подтверждено** | S9: единицы микросекунд |
| Запрет HTTP | статически или в рантайме | **статически** | S11 |
| Кеш модулей (LRU) | MVP | **без изменений** | S6: 0.25 МиБ на модуль, сотни модулей помещаются |

## Целевой SLO data plane

Для тёплого вызова тривиального скрипта на эталонной машине (Linux, 4 vCPU), при параллельности не выше числа ядер:

- **накладные расходы платформы p99 ≤ 3 мс, p50 ≤ 0.5 мс** — включая HTTP, аутентификацию, обе проверки схем, пул и Extism;
- время исполнения самого скрипта — сверх этого и ограничено `timeout_ms` хука.

Текущая реализация укладывается с запасом около 50%: 1.0 мс p99 последовательно и 2.0 мс p99 при 4 клиентах (S12). Запас нужен, потому что общие раннеры CI шумные. После форка go-sdk (горячая точка аллокаций) цель MVP — p99 ≤ 1 мс при 4 клиентах.

Холодный путь (первый вызов тенанта после старта или переезда) SLO не покрывает: создание инстанса добавляет ~0.5 мс на Linux, компиляция вынесена в Preload.
