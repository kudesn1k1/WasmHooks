 консоль оператора ─┐
 консоль тенанта ───┴─► /api/v1/* ─► rewrite (F2) ─► control-plane :8000   api/control-plane.openapi.yaml

 С ним общаются только control plane и бэкенд магазина.

|---|---|

### Аутентификация

Два вида Bearer-токенов, у каждой консоли свой.

**Консоль оператора — ключ установки** (D19).

- Формат `whk_` + 32 символа.
- Тем же ключом бэкенд магазина ходит в API оператора и в data plane.
- Прав один уровень: ключ разрешает всё.
- Выпускается командой `controlplane apikey create`, после T2 — ещё и через API (F7).

**Консоль тенанта — JWT** (D18).

- Выписывает оператор: `POST /api/v1/tenants/{external_id}/console-sessions` с ключом установки. Ответ `201 {token, expires_at}`.
- Срок — час (`CP_TENANT_TOKEN_TTL_S`). Продления нет: когда срок истёк, консоль открывают заново.
- Claims: `sub` — `external_id` тенанта (`merchant-a`), `aud` — `tenant-console`.
- Тенант определяется только токеном, в путях `/tenant/*` его нет.

Чужой токен не подходит. Ключ установки на `/api/v1/tenant/*` и JWT тенанта на API оператора дают `401`. Любой `401` — это problem+json «Не авторизован» с заголовком `WWW-Authenticate: Bearer`.

### Ошибки

Все ошибки приходят как `application/problem+json` (RFC 9457): `{type, title, status, detail?}`.

- `title` написан по-русски, его можно показывать пользователю как есть.
- `detail` несёт подробности: имя хука, поле, хеш.
- Логика UI опирается на `status`, а не на текст.

| Статус | `title` | `detail` | Когда |
|---|---|---|---|
| 400 | Некорректный запрос | `<где>: <что>` | ошибка в пути или query |
| 401 | Не авторизован | — | нет токена, токен чужой или истёк |
| 404 | Хук не найден / Тенант не найден | имя | |
| 409 | Хук с таким именем уже есть | имя | `POST /hooks` |
| 409 | Нельзя сузить список разрешённых возможностей | убранные значения через запятую | `PUT /hooks/{name}` |
| 422 | Некорректный запрос | `<путь к полю>: <сообщение>`, только **первая** ошибка. Пример: `body.timeout_ms: Input should be greater than or equal to 1` | тело не по схеме |
| 422 | Невалидное определение хука | `input_schema: …`, `output_schema: …`, `sample_input: …` | data plane не скомпилирует JSON Schema, или пример входа ей не соответствует |
| 501 | Ещё не реализовано | номер задачи backend, например `T3` | заглушки |
| 500 | Внутренняя ошибка сервера | — | баг control plane |

Заголовки ошибок T1–T5 перечислены в критериях приёмки этих задач в `docs/handoff/backend.md`. Они совпадают с заголовками в моках консоли тенанта.

## 2. Как запустить против настоящего API

Нужен запущенный Docker Desktop. Команды даны для bash, на Windows — Git Bash. Запускать из корня репозитория.

```bash
docker compose up -d --build --wait control-plane
curl -s localhost:8000/readyz                # {"status":"ready"}

KEY=$(docker compose exec -T control-plane controlplane apikey create --name web)
echo "$KEY"                                  # whk_...; второй раз его не покажут
```

Имя ключа уникально. Если `web` уже занято, возьмите другое имя.

**Хук.** Возьмите тело `hook.json` из раздела «Первый хук» `docs/handoff/backend.md`:

```bash
curl -s -X POST localhost:8000/api/v1/hooks \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  --data @hook.json
```

После F3 хук можно завести и в консоли оператора.

**Тенант.** До T1 API тенантов нет, поэтому для разработки тенанта вставляют прямо в базу:

```bash
docker compose exec -T postgres psql -U wasmhooks -d controlplane \
  -c "INSERT INTO tenants (external_id, name) VALUES ('merchant-a', 'Merchant A')"
```

Это обход API, только для разработки. Версия снимка при такой вставке не растёт, и data plane узнает о тенанте лишь при следующем изменении конфигурации. Консоли тенанта это не мешает. Другие способы:

- после T1 — `POST /api/v1/tenants` или экран F7;
- после PR2 — `docker compose exec -T control-plane controlplane seed-demo`. Команде нужен хук `checkout.discount`. Она создаёт тенанта `merchant-a`, загружает проверенный `discount.wasm` и делает его активной версией.

**Токен консоли тенанта:**

```bash
curl -s -X POST localhost:8000/api/v1/tenants/merchant-a/console-sessions \
  -H "Authorization: Bearer $KEY"
# {"token":"eyJ...","expires_at":"..."}
```

**Next.js.** Этот шаг работает после F2. Имена переменных ниже — предложение из F2. Если выберете другие, поправьте этот раздел.

```bash
cd web
cat > .env.local <<'EOF'
NEXT_PUBLIC_API_MOCKING=partial
CONTROL_PLANE_URL=http://localhost:8000
EOF
npm run dev
```

Дальше: `http://localhost:3000/operator`, там нужен ключ `$KEY`, и `http://localhost:3000/tenant#token=<token>`.

До F2 браузер до control plane не достучится: CORS в control plane нет, и он не понадобится (решение в F2). Поэтому совет из `web/README.md` указать в `NEXT_PUBLIC_API_BASE_URL` адрес control plane не работает.

Остановить стенд и стереть данные: `docker compose down -v`.

## 3. Правила

1. **Контракт первым** (`docs/TEAM.md`).
   - Формы берутся из `api/control-plane.openapi.yaml`.
   - Файл генерируется из кода control plane, руками его не правят.
   - Нужна другая форма — пишите backend в issue или комментарии. Изменение придёт PR-ом, где вы ревьюер.
   - Внутри `/v1` изменения только добавляющие.
2. **Tolerant reader.**
   - Незнакомые поля ответа игнорируются. `z.object` по умолчанию их отбрасывает, `.strict()` не используйте.
   - Если поле в контракте `nullable` или необязательное, zod принимает и `null`, и отсутствие поля (`.nullish()`), если нет причины поступить иначе.
3. **Решения — по `status`, текст — пользователю.** `title` и `detail` показываются как есть. Разбирать `detail` ради логики нельзя.
4. **Секреты.**
   - Ключ установки и токен тенанта хранятся в `sessionStorage` своей консоли. Не в `localStorage`, не в cookie, не в query-строке и не в логах.
   - Токен тенанта приходит во фрагменте URL и сразу оттуда убирается (F4).
   - Выход из консоли стирает токен.
5. **Тенант — только из токена.** В консоли тенанта нет выбора тенанта ни в путях, ни в состоянии UI.
6. **Моки повторяют контракт и поведение.**
   - Обработчик MSW отвечает теми же статусами и заголовками ошибок, что настоящий API.
   - Обработчик проверяет, что пришёл `Authorization`.
   - Изменился контракт — мок меняется в том же PR.
7. **Одна задача — один PR.**
   - CI-джоба `web` зелёная: `typecheck`, `lint`, `test`, `build`.
   - Ревьюер — тимлид. Если PR задевает API или контракт backend, в ревьюерах ещё и backend.

## 4. Задачи F1–F9

### Порядок

```text
 сразу, без backend:  F1 ревью контракта
                      F2 прокси и токены ─┬─► F3 консоль оператора: хуки
                                          └─► F4 вход в консоль тенанта
 по мере backend:     F5 консоль тенанта на живом API  ◄── T6, T3, T4, T5
                      F6 конфиг привязки                ◄── T5 (до неё на моках)
                      F7 тенанты и ключи                ◄── T1, T2 (до них на моках)
 вместе с T7:         F8 витрина                        ◄── контракт магазина
 когда удобно:        F9 типы из контракта
```

Сроки задач определяет тимлид.

### Точки синхронизации с backend

| Событие | Backend | Frontend |
|---|---|---|
| сейчас | PR1 в ревью | F1: ревью контракта консолей |
| T1 смержена | тенанты через API | F7: тенанты с моков на API; тенант для ручных проверок больше не через psql |
| T2 | ключи через API | F7: ключи с моков на API |
| T6 (можно раньше, по просьбе фронтенда) | чтение хуков тенанта | F5: список хуков и страница хука с моков на API |
| T3 | загрузка модулей | F5: загрузка и список версий |
| T4 | валидация в фоне | F5: настоящие статусы и отчёт проверки. Нужен PR2 в compose |
| T5 | привязка | F5: активация и откат; F6: конфиг |
| T7, до кода | контракт `api/demo-shop.openapi.yaml` | F8: фронтенд предлагает формы как потребитель и ревьюит PR контракта |
| T7 | бэкенд магазина, «Мои скрипты» | F8: витрина с моков на API, вход в консоль тенанта из магазина |

Если T6 нужна раньше, скажите тимлиду: план backend это допускает.

### F1. Ревью контракта консолей

**Цель.** Подтвердить, что формы контракта подходят фронтенду, до того как backend начнёт по нему T1–T6. Позже изменение формы — это отдельный PR и переделка с обеих сторон.

**Что посмотреть** в `api/control-plane.openapi.yaml` из PR1. Если PR1 уже смержен, замечания оформите отдельным issue.

- Формы консоли тенанта взяты из моков и zod-схем `web/src/entities/*` поле в поле (спек M1, §6.7). Известные расхождения:
  - `ValidationCheck.detail` в контракте `string | null`, в zod — `.optional()`. У пройденных проверок сервер поле не передаёт, поэтому сегодня всё работает. Надёжнее перейти на `.nullish()`.
  - Хук оператора (`Hook`) не совпадает с `HookView` консоли тенанта. У `Hook` есть `created_at` и `updated_at`, а `sample_input` обязателен. Поэтому F3 нужна своя схема: `hookSchema` из `entities/hook` подходит только консоли тенанта.
  - `PUT .../binding` принимает ещё и `config` (объект строк). Это нужно для user story 3.2, экран — F6.
  - `/tenant/invocations` в контракт до MVP не входит.
- У эндпоинтов консоли тенанта в контракте описаны только 200/201, 400, 401 и 422. Коды 404, 409 и 413 из критериев T3–T5 появятся вместе с реализацией. Если они нужны в контракте сразу, попросите backend.
- Удобны ли формы для экранов F3, F6 и F7: списки `{items: [...]}`, имена полей, что возвращают `PUT` и `PATCH`.

**Готово, когда** ревью оставлено в PR1 (approve или комментарии), а договорённости по расхождениям записаны в PR или issue.

### F2. Прокси к control plane и токены

**Цель.** Консоли ходят в настоящий control plane с нужным токеном. На то, чего в API ещё нет, по-прежнему отвечает MSW.

**Критерии приёмки.**

- [ ] **Прокси.** В `next.config.ts` есть rewrite `/api/v1/:path*` → `${CONTROL_PLANE_URL}/api/v1/:path*`.
  - `CONTROL_PLANE_URL` — серверная переменная, по умолчанию `http://localhost:8000`.
  - В браузере `API_BASE_URL` остаётся `/api/v1`. Запросы идут на свой же origin, поэтому CORS не нужен. В control plane CORS не добавляем; вопрос из T6 в `docs/handoff/backend.md` закрыт этим решением.
  - Rewrites читаются при сборке: для `next build` переменная нужна уже на этапе сборки.
- [ ] **Заголовок.** `apiRequest` добавляет `Authorization: Bearer <токен>` текущей консоли.
  - На `/api/v1/tenant/*` идёт токен тенанта, на остальные пути — ключ установки.
  - Как это устроить (контекст, параметр, функция-поставщик токена), решаете вы.
  - `credentials: "include"` больше не нужен: API не использует cookie.
- [ ] **401.** Ответ `401` на любой запрос консоли стирает её токен и показывает экран входа этой консоли (F3, F4). Токен в лог не попадает.
- [ ] **501.** Ответ `501` показывается отдельным понятным состоянием («Ещё не реализовано на бэкенде: T3»), а не общей ошибкой. Тогда экраны можно показывать на демо, пока идут T-задачи.
- [ ] **Режимы моков** в `NEXT_PUBLIC_API_MOCKING`:
  - `all` (по умолчанию в `npm run dev`) — работают все обработчики MSW, бэкенд не нужен;
  - `partial` — MSW отвечает только за эндпоинты, которых в API ещё нет. Остальные запросы уходят дальше в прокси: `onUnhandledRequest: "bypass"` уже стоит;
  - `disabled` — MSW выключен.
- [ ] **Список «ещё нет в API»** живёт в одном явном месте кода, например `src/mocks/pending.ts` с группами обработчиков.
  - Каждая смерженная T-задача — это PR, который убирает её группу из списка.
  - Группа `invocations` остаётся в списке до MVP.
- [ ] **Авторизация в моках.** Обработчики MSW без `Authorization` отвечают `401`, как настоящий API. В режиме `all` подходит любой непустой токен.
- [ ] **README.** В `web/README.md` раздел «Моки API» описывает три режима и прокси.
- [ ] **Тесты** в `shared/api/http.test.ts`: заголовок `Authorization` для обеих консолей, поведение на `401` и на `501`.

**Не в объёме:** продление токена тенанта (в API его нет), CORS.

### F3. Консоль оператора: вход и хуки

**Работает против настоящего API уже сейчас.** Это user story 3.1 основного спека: оператор в консоли создаёт хук `checkout.discount`.

**Эндпоинты:** `GET/POST /api/v1/hooks`, `GET/PUT /api/v1/hooks/{name}`. Схемы: `Hook`, `HookCreate`, `HookSpec`, `HookList`. Аутентификация — ключ установки.

**Критерии приёмки.**

- [ ] **Вход.**
  - Если в `sessionStorage` нет ключа, консоль оператора показывает форму «Ключ установки».
  - Ключ проверяется запросом `GET /api/v1/hooks`. На `401` форма пишет «Ключ не подошёл».
  - Есть кнопка «Выйти».
  - Рядом с формой предупреждение: ключ даёт полный доступ к установке, вводить его можно только на своём компьютере.
- [ ] **Список хуков:** имя, `def_version`, `timeout_ms`, `memory_max_pages`, `updated_at`; из списка открывается хук.
- [ ] **Создание.** Форма содержит:
  - имя;
  - `input_schema`, `output_schema`, `sample_input` — редакторы JSON. Хватит textarea с проверкой `JSON.parse` и форматированием; CodeMirror или Monaco — по желанию;
  - `timeout_ms`, `memory_max_pages`;
  - `allowed_host_functions`, `allowed_effect_types` — списки строк.

  Успех — ответ `201`.
- [ ] **Проверки на клиенте** повторяют контракт. Окончательное решение за сервером.
  - Имя соответствует `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$` и не длиннее 128 символов.
  - `timeout_ms` от 1 до 30000.
  - `memory_max_pages` от 16 до 16384.
  - JSON-поля — объекты.
- [ ] **Ошибки.**
  - `422` выводится баннером над формой: `title` и `detail`.
  - `detail` содержит только первую ошибку (`body.timeout_ms: …`, `input_schema: …`, `sample_input: …`), поэтому подсвечивать по нему все поля не нужно.
  - `409` «Хук с таким именем уже есть» показывается у поля имени.
- [ ] **Редактирование.**
  - `PUT` получает тело `HookSpec`: все поля, кроме `name`. Лишнее поле даёт `422`.
  - После сохранения виден новый `def_version`.
  - Сохранение без изменений возвращает тот же `def_version`. В этом случае показать «Изменений нет».
- [ ] **Списки разрешённых возможностей только растут.**
  - Уже сохранённые значения в форме удалить нельзя.
  - Если пришёл `409` «Нельзя сузить список разрешённых возможностей», показать убранные значения из `detail`.
- [ ] **Моки.** Обработчики MSW для `/hooks` ведут себя так же (`201`, `404`, `409`, `422`), чтобы экран работал и в режиме `all`.
- [ ] **Тесты** (Vitest + RTL): создание, `409` на повторное имя, `422` с `detail`, запрет сужать списки.

**Не в объёме:**

- удаление хуков (в API его нет);
- просмотр модулей тенантов;
- конструктор схемы по полям.

**Полезно знать.** Изменение хука доходит до data plane примерно за секунду: это новая версия снимка. Уже загруженные модули тенантов при этом заново не проверяются (раздел 5).

### F4. Вход в консоль тенанта по токену

**Цель.** Мерчант попадает в консоль тенанта по ссылке из магазина (спек M1, §4.3) и работает с токеном, который выписал оператор.

**Критерии приёмки.**

- [ ] **Ссылка `/tenant#token=<jwt>`.**
  - Layout консоли тенанта читает токен из фрагмента и кладёт его в `sessionStorage`.
  - Затем фрагмент убирается из адреса (`history.replaceState`).
  - Фрагмент не уходит на сервер и не попадает ни в логи, ни в `Referer`. Так же устроены magic-ссылки App Portal в Svix.
- [ ] **Нет сессии.** Если токена нет или пришёл `401`, показывается экран «Сессия консоли не начата или истекла. Откройте консоль заново из магазина».
  - В `npm run dev` на этом экране есть подсказка, как получить токен (`curl` из раздела 2).
  - Там же есть поле, чтобы вставить токен руками.
- [ ] **Шапка** показывает тенанта (`sub` из payload JWT) и время окончания сессии (`exp`). Payload читается без проверки подписи: это только отображение, проверяет сервер.
- [ ] **Истечение срока.** Когда наступил `exp`, консоль сама показывает экран истёкшей сессии, не дожидаясь `401`.
- [ ] **Моки.** Ссылка `/tenant#token=mock` открывает консоль в режиме `all`.
- [ ] **Тесты:** токен из фрагмента сохраняется и пропадает из адреса; `401` ведёт на экран истёкшей сессии.

**Синхронизация с T7.** Кнопка «Мои скрипты» на витрине получает `{token, expires_at}` от бэкенда магазина и открывает `/tenant#token=…` (F8). Если backend предложит другой формат ссылки, договаривайтесь в контракте магазина.

**Как проверить сейчас.** Получите токен через `curl` (раздел 2) и откройте `http://localhost:3000/tenant#token=<token>`. До T6 экраны консоли тенанта в режиме `disabled` покажут «Ещё не реализовано», а в режиме `partial` — моки.

### F5. Консоль тенанта на живом API

**Цель.** Экраны консоли тенанта уже готовы на моках. Они по одному переходят на настоящий API по мере T6, T3, T4, T5. Это user stories 3.2 и 3.3 основного спека, кроме playground и графиков таймаутов (они в MVP).

На каждую T-задачу — маленький PR: группа обработчиков уходит из списка `pending` (F2), экран проверяется руками против compose.

| После | Экран | На что смотреть |
|---|---|---|
| T6 | список хуков, страница хука | схемы и `sample_input` из `HookView`; у хука без привязки `binding: null` |
| T3 | загрузка, список версий | `409` «Такая версия уже загружена» (`detail` — хеш); `413` «Модуль слишком большой»; `422` на пустой файл |
| T4 | статусы версий и отчёт проверки | цепочка `uploaded` → `validating` → `validated` или `rejected`; при отказе видна первая проваленная проверка и её `detail`. Нужен PR2 в compose |
| T5 | активация и откат | `409` «Активировать можно только проверенную версию» (`detail` — `Статус: …`); `404` «Версия не найдена». Откат — та же активация прежней версии |

Подробности по T3: лимит модуля 10 МиБ. Проверьте размер на клиенте до отправки: сервер всё равно примет тело целиком.

Подробности по T4:

- Опрос раз в 2 с, пока есть незавершённые версии, уже работает.
- Если data plane недоступен, версия долго остаётся в `validating`. Таймаута в UI не нужно, достаточно «проверяется».

**Готово, когда** для каждой строки таблицы:

- экран работает в режиме `partial` против compose с этой T-задачей;
- группа удалена из `pending`;
- моки для тестов остались.

**Ручная проверка T4–T5 целиком** (файлы лежат в `dataplane/testdata/wasm/`):

- `discount.wasm` → `validated` → активировать;
- `http-call.wasm` → `rejected`, проваленная проверка — `imports`.

Сквозной вызов `checkout.discount` после активации проверяет сценарий из `e2e/`.

### F6. Конфиг привязки

**Цель.** Мерчант задаёт параметры своего скрипта, например порог суммы прошлых покупок для скидки (user story 3.2). Скрипт читает их host-функцией конфига.

**Эндпоинт:** `PUT /api/v1/tenant/hooks/{hook}/binding` с телом `{config: {...}}`.

- `config` — объект строк.
- В том же запросе можно передать `active_module_id`.
- Ответ — `TenantBinding`.

**Критерии приёмки.**

- [ ] **Редактор** пар «ключ — значение» на странице хука.
  - Ключи непустые и уникальные.
  - Значения — строки. Числа мерчант вводит строкой, скрипт разбирает их сам.
- [ ] **Сохранение** отправляет только `config`. После ответа видны новый конфиг и `config_version`.
- [ ] **Без изменений.**
  - Тот же конфиг `config_version` не меняет; UI показывает «Изменений нет».
  - Тело без `active_module_id` и без `config` даёт `400` «Нечего менять». UI такое тело не отправляет.
- [ ] **Конфиг до активации.** Конфиг можно задать до активации версии.
- [ ] **Мок.** Мок `PUT .../binding` принимает `config` и меняет `config_version` по тем же правилам. Сейчас он `config` игнорирует.
- [ ] **Переход на API.** После T5 экран переходит на настоящий API, как в F5.

**Не в объёме** (всё это MVP):

- секреты в конфиге;
- типизированный конфиг по схеме;
- повторная проверка модуля с новым конфигом.

### F7. Консоль оператора: тенанты и ключи установки

**Цель.** Оператор заводит тенантов, меняет им квоты (user story 3.4), выпускает и отзывает ключи. До T1 и T2 экраны работают на моках по контракту.

**Эндпоинты:**

- `GET/POST /api/v1/tenants`, `GET/PATCH /api/v1/tenants/{external_id}`;
- `POST /api/v1/tenants/{external_id}/console-sessions` — уже работает;
- `GET/POST /api/v1/api-keys`, `DELETE /api/v1/api-keys/{key_id}`.

**Критерии приёмки.**

- [ ] **Тенанты.**
  - Список.
  - Создание: `external_id`, `name`, квоты. На повторный `external_id` приходит `409`.
  - Правка `name` и квот через `PATCH`: отправляются только изменённые поля.
  - Квота 0 означает значение по умолчанию data plane.
- [ ] **«Открыть консоль тенанта».** Кнопка вызывает `console-sessions` и открывает в новой вкладке `/tenant#token=…`. Для тенанта, вставленного через psql (раздел 2), работает уже сейчас.
- [ ] **Ключи.**
  - Список с `revoked_at`.
  - Создание. Токен показывается один раз, с кнопкой «Скопировать» и предупреждением, что больше его не покажут.
  - Отзыв с подтверждением: `DELETE` → `204`.
  - Если отозвать ключ, которым вошли, следующий запрос выведет из консоли.
- [ ] **Моки** следуют контракту и повторяют поведение из критериев T1 и T2 в `docs/handoff/backend.md`. После T1 и T2 экраны переходят на API, как в F5.

**Не в объёме:** удаление тенантов, права ключей (MVP).

**Критерии приёмки.**

## 5. Ограничения M1, которые вас касаются

Это осознанные компромиссы PoC (§14 спека M1), а не баги.

- Ключ установки в браузере даёт полный доступ к установке. Учётные записи и роли операторов — в MVP.
- Токен тенанта нельзя отозвать: он живёт до `exp` (час) и не продлевается.
- Лог вызовов (`/tenant/invocations`), playground и графики появятся в API только в MVP. Экран лога остаётся на моках.
- Квоты тенантов хранятся и доходят до data plane, но не применяются (MVP).
- Изменение схем и лимитов хука не перепроверяет уже привязанные модули.
- Сервер принимает тело загрузки целиком и только потом проверяет размер. Проверка на клиенте экономит мерчанту время.
- Пока data plane недоступен, версия может оставаться в `validating` сколько угодно: control plane повторяет проверку с бэкоффом.
