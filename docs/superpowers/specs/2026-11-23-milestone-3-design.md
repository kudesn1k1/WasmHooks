# M3. Потеря исполнителя под нагрузкой

Согласованные границы и критерии приёмки, 23 ноября 2026. База — `main` после T7 (`63dcf62`). Основание — [история 3.5](2026-09-04-wasm-extension-platform-design.md#35-платформа-переживает-потерю-исполнителя) и [решения о перегрузке в M2](../../adr/0005-admission-control.md).

## Результат для оператора

Магазин продолжает оформлять покупки во время потери pod-а исполнителя. По ответу чекаута видно, какую скидку посчитал скрипт и в каких случаях магазин применил fallback. По отчёту платформы видно, куда переехали вызовы, какой ценой и когда восстановилось обслуживание. Успешный HTTP-ответ магазина сам по себе ещё не доказывает, что хук сработал.

## Границы

- Выбран **kind**. Compose остаётся средой локальной разработки и регрессионного e2e. Приёмочный стенд включает control plane, PostgreSQL, MinIO, один gateway, три executor-а и демо-магазин T7. Один образ Go может поддерживать разные роли запуска. Gateway и executor в kind должны иметь независимые процессы и жизненные циклы.
- Магазин вызывает существующий HTTP Invoke API. Gateway проверяет запрос, применяет квоты M2 и общий ограничитель незавершённых вызовов. Внутренний Execute работает по gRPC, переносит отмену и дедлайн. Gateway фиксирует tenant, hook, версии определения и конфига, хеш модуля и ключ идемпотентности на весь вызов. Для Validate control plane использует действующий внутренний HTTP-контракт через сервис executor-ов. Gateway и executor-ы получают снимки самостоятельно.
- Gateway находит готовые executor-ы через headless Service и проверяет их здоровье. Consistent hashing с виртуальными узлами назначает владельца каждой паре `(tenant_id, hook)`. Исполнитель может обслужить перенаправленный вызов и на холодном кеше. По изменению кольца executor предзагружает модули своих пар. Пулы, слоты и изоляция M2 действуют на каждом исполнителе.
- На транспортном сбое или явном отказе до запуска из-за перегрузки допускается один повтор на другом здоровом узле при достаточном остатке исходного дедлайна. Повтор использует исходные версии и считается одним логическим вызовом для квот. `quota_exceeded`, ошибка или таймаут гостя завершают вызов. Circuit breaker на gateway, отдельно для каждой пары, временно отсекает повторяющиеся сбои самого скрипта и допускает пробный вызов после cooldown. Потеря pod-а не должна открывать breaker мерчанту.
- Метрики и отчёт покрывают исходы, p99, число попыток, успешные повторы, состав кольца и распределение вызовов по executor-ам. Полная Grafana-витрина, пользовательский журнал и playground, SDK, Helm для поставки и распределённые квоты остаются отдельными задачами MVP.

## Definition of Done

Публичный контракт Invoke гарантирует для ответа `503 unavailable`, что скрипт не запускался. При потере ответа gRPC исполнитель уже мог завершить вызов. В M3 gateway возвращает `502 problem+json`, когда после допустимых попыток результат остаётся неизвестным и хотя бы одна попытка могла стартовать. При подтверждённом отказе до запуска остаётся `503 unavailable`. В обоих случаях магазин применяет fallback. Это различие закреплено в OpenAPI и тесте клиента T7. Открытый breaker возвращает `503 unavailable` с причиной в диагностике и без повторной отправки. Это уточняет исходную таблицу отказов, где для открытого breaker-а планировался исход предыдущей ошибки гостя.

1. **Воспроизводимый запуск.** Из чистого выделенного кластера kind документированная команда разворачивает стенд и запускает сценарий с кодом выхода PASS/FAIL. Сценарий создаёт привязки через публичные API управления. Для магазинов T7 настроены разные заранее известные скидки. Обычный чекаут возвращает ожидаемую сумму и `fallback=false`.
2. **Исходное распределение.** Набор тестовых пар покрывает все три executor-а. Под постоянной нагрузкой фиксируем базовые p99 и исходы, владельца каждой пары, состав кольца и идентификаторы pod-ов. При стабильном кольце и здоровых узлах последовательные вызовы пары идут к одному владельцу.
3. **Потеря узла.** Во время нагрузки принудительно завершаем один executor. В отдельном интервале наблюдения замена ещё не участвует в кольце. Gateway исключает потерянный узел. Среди пар с изменившимся владельцем есть все и только пары погибшего узла. После сходимости все тестовые пары возвращают ожидаемый результат, запросы больше не направляются погибшему узлу. Готовая замена автоматически входит в кольцо и получает свою долю вызовов.
4. **Повтор и изоляция ошибок.** Детерминированная интеграционная проверка обрывает первую попытку и показывает успешную вторую на другом узле. Если на повтор не осталось времени, подтверждённый отказ до старта даёт 503, потеря ответа после возможного старта — 502. На один Invoke приходится максимум две попытки с общим дедлайном. Для сломанного скрипта отдельно проверяются открытие breaker-а, быстрый отказ, пробный вызов и восстановление. Здоровая пара продолжает исполняться.
5. **Доказательства.** К поставке приложен реальный отчёт прогона kind с параметрами нагрузки, идентификатором ревизии и тремя фазами — до отказа, переход, восстановление. Он показывает `ok`, `unavailable`, fallback магазина, p99, успешные повторы, переехавшие пары и время сходимости. Отказы в переходном окне учитываются. Условия PASS после сходимости — все ожидаемые скидки верны, ноль fallback и ноль ошибок на фиксированной проверочной серии при нагрузке ниже ёмкости двух узлов. Отдельно проходят тесты публичных контрактов и существующий Compose e2e.

В T7 ровно два магазина. Их чекауты проверяют бизнес-результат, а дополнительные зарегистрированные тестовые тенанты вызывают тот же хук через Invoke и позволяют покрыть все три executor-а. Для удаления выбираем владельца хотя бы одного из магазинов. Чтобы воспроизводимо увидеть переход 3 → 2 → 3, на выделенном kind-стенде временно закрываем планирование новых pod-ов на узлах, где может стартовать замена (`cordon`), удаляем выбранный pod и после проверки открываем планирование. Сценарий восстанавливает исходное состояние планирования и при ошибке.

До допуска замены проверочная серия на двух executor-ах обязательна, включая покупку в затронутом магазине. На всём протяжении опыта ошибочная скидка, ошибка HTTP чекаута или потерянный ответ магазина дают FAIL. В переходном окне допускается явно помеченный fallback с нулевой скидкой. Его доля публикуется отдельно. Предзагрузку проверяем на дополнительной паре с отдельным модулем и первым запросом после смены владельца. У нового владельца должна быть запись об успешной компиляции этого хеша до запроса.

Параметры прогона (RPS, длины фаз, число пар, интервалы discovery и health, бюджет retry, пороги breaker-а) указываются в конфигурации и сохраняются с отчётом. Порог ожидания сходимости задаётся до запуска, его превышение даёт FAIL. Замер p99 устанавливает базу для распределённого пути. Численный SLO M2 измерялся для вызова внутри одного процесса.
