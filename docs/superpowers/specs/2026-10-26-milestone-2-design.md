# Milestone 2: шумный тенант — квоты и admission control в data plane

Design-спецификация вехи. Дата: 2026-10-26. Контрольная точка: 2026-10-27.

Основной спек: `2026-09-04-wasm-extension-platform-design.md` (user story 3.4, §9, §11.3). Спек M1: `2026-10-09-milestone-1-design.md` (набросок S7b в §11). Где документы расходятся, прав этот.

---

## 1. Цель

Сделать правдой user story 3.4 основного спека со стороны data plane: тенант, который шлёт в сто раз больше вызовов или чьи скрипты зависают, упирается в свои квоты и получает `quota_exceeded`, а латентность и исходы остальных тенантов не меняются. Оператор меняет квоту в control plane, и она применяется без перезапуска.

Почему сейчас. Спайк S7b показал, что без ограничения исполняемых вызовов изоляция под нагрузкой не держится: когда крутящихся скриптов больше, чем ядер, таймауты опаздывают на 67–85 мс, сосед ждёт до 60 мс (Linux, `docs/spike-results.md`). Квоты тенанта уже есть в control plane (T1, `PATCH /api/v1/tenants/{id}` поднимает версию снимка) и доходят до data plane, но data plane `rate_limit_rps` игнорирует, а `concurrency_limit` понимает как лимит инстансов на ключ пула. Это единственная недостающая часть истории 3.4: консоль оператора (F7), скидка по умолчанию в SDK (T8) и витрина (T7, F8) — задачи команды, которые она доделывает в своей ветке.

Порядок относительно масштабирования (история 3.5, M3): кольцо по (тенант, хук) сажает горячего тенанта на один executor, а повтор на соседе без отсечки превращается в шторм ретраев. Сначала узел должен честно отказывать под перегрузкой, потом масштабироваться. Образцы: Google SRE book, главы Handling Overload и Addressing Cascading Failures; Kubernetes API Priority and Fairness; AWS Builders' Library, «Fairness in multi-tenant systems».

Вся работа M2 на тимлиде; задачи команды (T7, T8, F5–F9) идут параллельно в её ветке и в DoD M2 не входят.

## 2. Definition of Done

Каждый пункт проверяется тестом, замером или шагом демо.

1. **Лимит исполняемых вызовов (S7b).** В executor-е слоты по CPU: `max(1, GOMAXPROCS−1)` по умолчанию, доля одного тенанта `max(1, слоты/2)`. Ожидание слота ограничено дедлайном вызова и длиной очереди; не дождался — `unavailable`, скрипт не запускался. *Доказательство:* повторный замер S7b в workflow `bench` на Linux (раздел 9.2): A/B «слоты включены — выключены» в одном прогоне, N = ядра и N = 4×ядра. Цель (уточняется после первого прогона): промах таймаута у запущенных скриптов max ≤ 5 мс, p99 соседа ≤ базовый + 5 мс, ни одного `timeout` из-за насыщения.
2. **Квоты тенанта из снимка на gateway.** `rate_limit_rps` — token bucket, пустой bucket даёт немедленный `quota_exceeded`. `concurrency_limit` — одновременные вызовы тенанта; сверх лимита ограниченное ожидание, затем `quota_exceeded`. *Доказательство:* unit-тесты пакетов и тесты gateway.
3. **Перегрузка узла.** Очередь за слотами ограничена, при переполнении — немедленный `unavailable`. Тенант сверх квоты не может вызвать у других ни `unavailable`, ни роста латентности: и слоты, и места в очереди ограничены долей тенанта. *Доказательство:* интеграционный тест executor-а с настоящими wasm-модулями.
4. **Изменение квоты применяется без перезапуска.** *Доказательство:* шаг e2e: `PATCH` квоты тенанта, через ≤ 1 с вызовы сверх новой квоты получают `quota_exceeded`; снятие квоты возвращает `ok`.
5. **Нагрузочный сценарий «шумный тенант».** Генератор нагрузки на Go, только stdlib, `e2e/cmd/loadgen`, против compose. Фаза «тихо»: merchant-a один. Фаза «шумно»: merchant-a с той же нагрузкой плюс merchant-b в 100 раз больше. Отчёт по тенантам и фазам: p50/p99/max и таблица исходов; код выхода 1, если нарушены пороги раздела 9.3. Прогон на Linux в CI. *Доказательство:* у merchant-a 100% `ok` в обеих фазах и p99 в пределах порога, у merchant-b `quota_exceeded`.
6. **Хвост M1 закрыт.** Сценарий e2e проводит модуль по пути T3–T5 через API control plane: тенант, токен консоли, загрузка `discount.wasm`, фоновая валидация до `validated`, активация привязки, вызов `ok`. Шаг с `seed-demo` удаляется из сценария.
7. **Документы.** ADR 0005 по admission control; контракты (`api/dataplane-internal.openapi.yaml`, `api/invoke.openapi.yaml`) и `dataplane/README.md` описывают новые смыслы полей и исходов; результат S7b в `docs/spike-results.md`; две свежие ревью в `docs/reviews/`; разбор вехи для тимлида вне репозитория (`D:\Uni\WasmHooks-M2-разбор.pdf`). CI зелёный на PR.

### Не входит в M2

Circuit breaker (связан с повтором на соседе — M3). Общий лимит одновременных вызовов на gateway: в одном процессе узел защищает очередь за слотами executor-а, лимит gateway появляется вместе с разделением процессов. Prometheus и Grafana: доказательство истории 3.4 — отчёт генератора. Разделение gateway и executor, кольцо, повторы, Kubernetes. Распределённый rate limit: квоты считаются на реплику gateway (основной спек §11.3). Go SDK. Слоты на компиляцию модулей. Изменения в control plane, консолях, SDK и демо-магазине.

## 3. Решения от 2026-10-26

| # | Решение | Почему |
|---|---|---|
| D27 | `concurrency_limit` тенанта означает одновременные вызовы тенанта на реплике gateway, по всем его хукам. Лимит инстансов на ключ пула становится внутренней деталью executor-а. | Квота для оператора естественна в вызовах тенанта, инстансы — деталь реализации пула. Контракт ещё молодой, менять смысл поля сейчас дёшево. |
| D28 | Вызов, не дождавшийся слота, получает `unavailable`, а не опоздавший `timeout`. Ожидание до запуска (очередь квоты параллельности и очередь за слотом) тратит только ту часть дедлайна, что сверх лимита хука, а очередь за слотом — ещё 5 мс меньше, в запас на создание инстанса: допущенный скрипт получает полный лимит (ревью 1, I1; ревью 2, m1). | `unavailable` значит «скрипт не запускался, узел перегружен» — честный сигнал к масштабированию и к повтору на другом узле в M3. Опоздавший `timeout` обвиняет тенанта в том, в чём он не виноват. |
| D29 | Квоты тенанта применяются на gateway, слоты по CPU — в executor-е. | Квота — бизнес-политика оператора и проверяется на входе, до траты ресурсов. CPU — физический ресурс executor-а; после разделения процессов каждый executor защищает свои ядра сам. |
| D30 | Слоты: ёмкость `max(1, GOMAXPROCS−1)`, доля тенанта `max(1, слоты/2)`, очередь ограничена и тоже делится долями; освободившийся слот получает ждущий тенант с наименьшим числом занятых слотов, при равенстве — тот, кому дольше не выдавали слот, затем самый старый ждущий (ревью 1, I2). При `GOMAXPROCS = 2` ёмкость 2 (доля 1): наблюдатель делит P со слотом, зато сосед зависшего тенанта не получает отказов (ревью 2, I2). Если доля не меньше ёмкости или ёмкость не меньше `GOMAXPROCS`, data plane пишет предупреждение при старте. | Код wasm не вытесняется. Один свободный P нужен наблюдателю отмены wazero, чтобы закрыть модуль по дедлайну (S7b). Доля не даёт одному тенанту занять все слоты и очередь; выдача по наименьшей занятости — справедливая очередь в духе Kubernetes APF, без отдельной очереди на каждого тенанта. |
| D31 | Слот захватывается до аренды инстанса из пула и отпускается, когда инстанс вернулся в пул. | Ждущий вызов не держит инстанс и его память. Создание инстанса — тоже работа CPU. Число инстансов ключа ограничено числом слотов тенанта. |
| D32 | `rate_limit_rps = 0` значит «без ограничения частоты»: bucket у тенанта нет, при переходе к конечной частоте создаётся новый полный. Ёмкость bucket — `max(1, rate_limit_rps)`, секунда запаса. | В M0–M1 поле игнорировалось и по умолчанию равно 0; другое толкование нуля сломало бы существующие установки. |
| D33 | Генератор нагрузки — Go-программа на stdlib в `e2e/`, не k6. | k6 не установлен; Go-программа запускается в той же джобе CI, что e2e, и считает перцентили так же, как спайки. |

## 4. User stories M2

### 4.1 Распродажа у одного мерчанта

merchant-b устраивает распродажу, его чекауты вырастают в сто раз. Gateway пропускает его вызовы в пределах `rate_limit_rps`, остальные сразу получают `quota_exceeded` (HTTP 429); магазин применяет скидку по умолчанию. Вызовы merchant-a идут с той же латентностью и теми же исходами, что до распродажи.

### 4.2 Зависший скрипт под нагрузкой

Новая версия скрипта merchant-b зависает на каждом вызове. Его вызовы держат не больше половины слотов executor-а, каждый ровно до своего таймаута; остальные вызовы merchant-b ждут в своей доле очереди или получают `unavailable`/`quota_exceeded`. merchant-a получает слот без ожидания, его таймауты срабатывают вовремя.

### 4.3 Оператор поднимает квоту

Оператор узнаёт, что merchant-b упирается в квоту, по ответам 429 в своём магазине (в M2 платформа не ведёт счётчиков отказов, они придут с метриками M3), и поднимает `rate_limit_rps` в консоли (F7, команда) или через API. Через долю секунды отказов становится меньше, data plane не перезапускался.

### 4.4 Узел перегружен целиком

Нагрузка всех тенантов вместе превышает то, что успевает CPU одного узла. Очередь за слотами заполняется, сверх неё вызовы сразу получают `unavailable`; латентность принятых вызовов не растёт. Оператор видит долю `unavailable` и добавляет мощность.

## 5. Путь вызова M2

```
HTTP → gateway: аутентификация → хук → схема входа → привязка (иначе no_handler)
     → дедлайн вызова
     → квота частоты тенанта        (пусто → quota_exceeded, reason rate_limit)
     → квота параллельности тенанта (ожидание в очереди тенанта не дольше дедлайн − лимит хука → quota_exceeded, reason concurrency_limit)
     → executor: снимок, модуль
       → слот CPU                   (очередь полна → unavailable, reason overloaded; кончился запас → unavailable, deadline_before_start)
       → аренда инстанса → вызов гостя → слот отпущен
       → проверка выхода
     ← квота параллельности отпущена
```

Квота параллельности держится от входа в gateway до возврата из executor-а, слот — от аренды инстанса до конца вызова гостя.

## 6. Gateway: квоты тенанта

Пакет `dataplane/internal/gateway/quota`, без внутренних зависимостей (правило в `internal/archtest`).

- `quota.Manager` хранит состояние по тенантам: token bucket (`golang.org/x/time/rate`) и счётчик одновременных вызовов с очередью ждущих.
- `Admit(ctx, tenantID, limits) (release func(), outcome)`: лимиты передаются при каждом вызове из текущего снимка, поэтому изменение квоты применяется со следующего вызова. Если лимит частоты или параллельности изменился, состояние тенанта обновляется на месте (`SetLimit`/`SetBurst`; рост лимита параллельности будит ждущих).
- Порядок: сначала частота (немедленный отказ, ожидания нет), потом параллельность. Вызов, отклонённый по параллельности, токен частоты уже потратил — так проще и консервативнее.
- Очередь параллельности тенанта: FIFO длиной `concurrency_limit`; переполнение — немедленный `quota_exceeded`. Ожидание ограничено контекстом вызова; истёк — `quota_exceeded` с `reason: concurrency_limit`; ушёл вызывающий — `unavailable` с `reason: caller_canceled`, как в executor-е.
- Состояние создаётся лениво для тенанта с привязкой (вызов без привязки получает `no_handler` раньше и квот не касается). Состояние удаляется, когда у тенанта нет вызовов в полёте, нет ждущих и bucket полон: новое состояние с полным bucket неотличимо от удалённого, поэтому удаление не сбрасывает квоту, а map не растёт с числом когда-либо звонивших тенантов. Проверка — при отпускании вызова.
- Новые reason: `rate_limit`, `concurrency_limit` (для `quota_exceeded`).

## 7. Executor: слоты CPU

Пакет `dataplane/internal/slots`, без внутренних зависимостей.

- `slots.New(Options{Capacity, TenantShare, Queue int})`. По умолчанию `Capacity = max(1, GOMAXPROCS−1)`, доля тенанта на слотах `TenantShare = max(1, Capacity/2)`, `Queue = 4×Capacity`, доля тенанта в очереди `max(1, Queue/2)`.
- `Acquire(ctx, tenantID) (release func(), err error)`: слот свободен и тенант ниже доли — сразу. Иначе, если в очереди есть место всего и в доле тенанта, — ждать; иначе `ErrOverloaded`. Ожидание ограничено `ctx`.
- Освобождение слота отдаёт его ждущему с наименьшим числом занятых слотов тенанта среди тех, кто ниже доли; при равенстве — самому старому. Отмена ожидания не теряет слот, выданный в момент отмены (тест на гонку обязателен).
- Executor берёт слот до `pool.Acquire` и отпускает после `Call`, как только инстанс вернулся в пул, до разбора выхода (иначе следующий вызов того же тенанта ждал бы в пуле возврата инстанса). `ErrOverloaded` → `unavailable` с `reason: overloaded`; истёк `ctx` → существующий `notStarted`.
- Лимит инстансов на ключ пула (параметр `limit` у `pool.Acquire`) — доля тенанта на слотах. `config.DefaultConcurrencyLimit` (4) остаётся значением по умолчанию квоты параллельности тенанта.
- Флаги бинарника: `-exec-slots`, `-exec-tenant-share`, `-exec-queue` (0 — по умолчанию). В лог при старте пишутся итоговые значения.
- `Stats()` (занято, ждут) для тестов и замеров.

## 9. Доказательства

### 9.1 Тесты

- `slots`: доля тенанта, длина очереди и её доли, выдача по наименьшей занятости, отмена ожидания, гонка отмены и выдачи, `-race`.
- `quota`: bucket, ожидание параллельности и отказ при переполнении, изменение лимитов на лету (снижение и повышение), очистка состояния.
- `gateway`: исходы `quota_exceeded` с reason, отпускание квоты на всех путях (включая ошибки executor-а).
- `executor` (настоящие wasm): merchant-b запускает 4×слоты вызовов `infinite-loop`, одновременно merchant-a — серию `discount`. Все вызовы merchant-a `ok`; запущенные вызовы merchant-b — `timeout` с промахом в пределах порога; не запущенные — `unavailable`. Порог промаха на CI-машине с запасом, точные числа даёт `bench`.
- `cmd/dataplane`: флаги и значения по умолчанию.

### 9.2 Замер S7b после

`TestSpikeAdmissionUnderSaturation` и `TestSpikeAllSlotsSpinning` в `internal/executor` (флаг `-spike`), на уровень выше старого S7b: настоящий рантайм, executor, пул, без HTTP. Через HTTP промах таймаута не измерить честно: время ответа включает ожидание слота, а reason клиенту не возвращается. Каждая конфигурация насыщается 2 с, merchant-a вызывается раз в миллисекунду, в выводе — число замеров. Первый тест: один шумный тенант (merchant-b, `infinite-loop`, `timeout_ms: 50`) держит N ∈ {ядра, 4×ядра} одновременных вызовов; A/B в одном прогоне — слоты по умолчанию против `Slots: nil` (без admission control; это не M1, где ещё был лимит инстансов на ключ пула). Второй тест (ревью 2, I1): все слоты заняты зависшими скриптами нескольких тенантов, ёмкость `GOMAXPROCS−1` против `GOMAXPROCS` — прямая проверка D30. Workflow `bench` запускается на push в ветку вехи, ещё раз с `GOMAXPROCS=2`; результат — в `docs/spike-results.md` рядом со старым S7b. S12 в том же прогоне показывает цену доли тенанта для одного тенанта (раздел 11).

### 9.3 E2E и генератор нагрузки

Сценарий e2e (`e2e/internal/scenario`) получает шаги:

- путь T3–T5 через API вместо `seed-demo` (DoD 6);
- `PATCH` тенанта `rate_limit_rps: 5`, затем 30 вызовов подряд: есть `quota_exceeded` (HTTP 429), не позже 1 с после ответа `PATCH`; `PATCH rate_limit_rps: 0` — вызовы снова `ok` (DoD 4).

`e2e/cmd/loadgen` (DoD 5) готовит тенантов через API тем же путём T3–T5 (merchant-a и merchant-b с `discount.wasm`; у merchant-b `rate_limit_rps: 50`) и гоняет фазы по 10 с: «тихо» — merchant-a 50 вызовов/с; «шумно» — merchant-a 50 вызовов/с плюс merchant-b 5000 вызовов/с (открытая модель нагрузки: вызовы по расписанию, не по ответам). Пороги для кода выхода, по умолчанию с запасом на шумный общий раннер CI и Docker: у merchant-a 100% `ok` в обеих фазах; p99 merchant-a в «шумно» ≤ p99 в «тихо» + 10 мс; у merchant-b доля `quota_exceeded` > 90% и ни одного `timeout`. Пороги — флаги. Запускается в джобе `e2e` после сценария.

## 11. Что гарантируется и что нет

- Один шумный тенант (поток вызовов или зависшие скрипты) не меняет исходы и латентность остальных: его ограничивают квоты на gateway и доля слотов и очереди в executor-е.
- Цена статической доли: один тенант даже на свободной машине исполняет не больше `TenantShare` вызовов одновременно (на 4 vCPU: слотов 3, доля 1). Пропускная способность одного тенанта ниже, чем в M0; это видно в S12. Доля настраивается флагом `-exec-tenant-share`. Уточнение на M3: доля, которая действует только пока ждут другие тенанты (work-conserving), ценой ожидания до одного вызова для новичка.
- Несколько одновременно зависших тенантов вместе могут занять все слоты и всю очередь: CPU конечен. Два шумных тенанта заполняют очередь своими долями, и третий тенант, которому пришлось бы ждать, сразу получает `unavailable/overloaded` (ревью 1, M1). Полностью это закрывают circuit breaker (M3), доля очереди, сжимающаяся с числом ждущих тенантов, и добавление мощности.
- При `GOMAXPROCS = 2` слотов два и свободного P для наблюдателя нет: промах таймаута зависших скриптов растёт до единиц миллисекунд, зато соседи изолированы. При `GOMAXPROCS = 1` слот один, изоляции нет: сосед зависшего тенанта получает `unavailable/deadline_before_start` примерно на каждом втором вызове (ревью 2, I2).
- Когда все слоты заняты зависшими скриптами нескольких тенантов, сосед ждёт слот до одного лимита хука (по замеру «все слоты крутятся», `docs/spike-results.md`).
- Отказы gateway (`quota_exceeded`) не попадают в записи о вызовах и лог: их видит клиент. Счётчики по (тенант, исход) — с метриками в M3 (ревью 1, M5).
- Вызов сверх квоты оплачивает разбор и проверку тела по схеме до отказа: порядок проверок M0 (404 → 400 → `no_handler` → квоты) сохранён (ревью 1, M6).
- Квоты считаются на реплику gateway; при нескольких репликах фактический лимит — лимит × реплики (основной спек §11.3).
- Компиляция модулей и Validate идут вне слотов: массовый холодный старт новых модулей может нагрузить CPU мимо admission control.
- Замеры задержек — только Linux (`docs/spike-results.md`, методическая оговорка).
