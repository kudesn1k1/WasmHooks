# WasmHooks: self-hosted платформа исполнения WebAssembly-расширений

Design-спецификация. Дата: 2026-09-04. Статус: на ревью команды.

Рабочее название WasmHooks, финальное имя выберем позже. Документ фиксирует принятые решения и границы. Всё, что здесь не описано как PoC или MVP, в этом семестре не делается.

Решения от 2026-09-24 см. в спеке M0, раздел 3; ниже они уже применены.

---

## 1. Цель и контекст

Учебный проект по дисциплине «Проектный практикум», осенний семестр 2026, продолжение в весеннем семестре. Требование преподавателя: архитектурно корректное решение, объяснимое и доказуемое с точки зрения масштабирования и отказоустойчивости.

Продукт: self-hosted платформа, которая позволяет SaaS-приложению безопасно исполнять кастомную логику своих клиентов в заранее определённых точках расширения. Клиенты загружают скомпилированные WebAssembly-модули, платформа исполняет их в изоляции с лимитами и возвращает результат приложению.

Предмет проекта не WebAssembly-рантайм, он берётся готовый. Предмет проекта инфраструктура вокруг рантайма: мультитенантность, квоты, масштабирование исполнителей, отказоустойчивость, версионирование, наблюдаемость.

Прототипы из индустрии: Shopify Functions (чистые функции без побочных эффектов, платформа применяет результат), Cloudflare Workers и Fastly Compute (изолированное исполнение на краю), Extism (универсальная плагинная система на wasm с host-функциями), Fermyon Spin и wasmCloud.

## 2. Термины

- **Платформа.** Наш продукт целиком: control plane, gateway, executor, SDK, консоли.
- **Оператор.** SaaS-приложение, развернувшее платформу у себя. Единственный, кто вызывает data plane. Одна установка платформы обслуживает одного оператора (решение D1, спек M0).
- **Тенант.** Клиент оператора. Пишет и загружает скрипты. Идентифицируется в вызовах значением `external_id`, которое задаёт оператор и которое уникально в пределах установки (решение D2, спек M0).
- **Хук.** Точка расширения, определённая оператором: имя (например `checkout.discount`), JSON-схема входа, JSON-схема выхода, лимит времени, лимит памяти, список разрешённых host-функций, список разрешённых типов эффектов, пример входа для валидации.
- **Скрипт.** WebAssembly-модуль тенанта, прикреплённый к хуку. У пары «тенант, хук» либо ровно одна активная версия скрипта, либо ни одной.
- **Вызов.** Одно синхронное исполнение скрипта по запросу оператора.
- **Host-функция.** Функция, которую платформа предоставляет скрипту через импорт wasm-модуля.
- **Эффект.** Желаемое изменение мира, которое скрипт возвращает как данные в выходе. Скрипт эффекты не совершает, их применяет оператор (в этом семестре) или платформа (в roadmap).
- **Снимок конфигурации.** Версионированное состояние control plane, необходимое data plane: определения хуков, активные привязки «тенант, хук, версия скрипта» вместе с конфигом тенанта на этом хуке, квоты тенантов.
- **Control plane.** Компонент, который решает, что разрешено. Работает в масштабе минут, не стоит на пути вызова.
- **Data plane.** Gateway и executor-ы. Решают, что происходит прямо сейчас, работают в масштабе миллисекунд.

## 3. User stories

### 3.1 Оператор подключает платформу

Разработчик магазина разворачивает платформу через Helm-чарт рядом с магазином. В консоли оператора создаёт хук `checkout.discount`: вход содержит корзину, клиента и сумму его прошлых покупок, выход содержит размер скидки в процентах и причину. Лимит 50 мс и 16 МиБ (числа для примера, реальные после спайка). Разрешённые host-функции: лог и конфиг. Разрешённые эффекты: нет. Получает API-ключ data plane, подключает SDK и в коде чекаута пишет один вызов с дедлайном и скидкой по умолчанию равной нулю. Магазин работает без изменений, пока ни один тенант не загрузил скрипт: платформа возвращает исход `no_handler`, SDK отдаёт значение по умолчанию.

### 3.2 Тенант кастомизирует скидку

Мерчант в консоли тенанта видит список хуков оператора со схемами и примером входа. Скачивает шаблон проекта на Rust, реализует функцию: если сумма прошлых покупок больше порога из конфига, скидка 10%. Собирает wasm, загружает в консоль. Платформа валидирует модуль: размер, экспорты, импорты, пробный вызов на примере входа. Мерчант видит отчёт валидации, задаёт порог в конфиге, проверяет скрипт в playground на своём входе, активирует версию. Следующий чекаут этого мерчанта считает скидку его скриптом.

### 3.3 Тенант выкатывает сломанную версию и откатывается

Мерчант загружает вторую версию с бесконечным циклом при пустой корзине. Валидация на примере входа проходит, версия активируется. На боевых вызовах с пустой корзиной скрипт убивается по дедлайну, магазин получает исход `timeout` и применяет скидку по умолчанию, чекаут не ломается. После серии таймаутов circuit breaker на паре «тенант, хук» переводит вызовы в быстрый отказ. Мерчант видит в консоли рост таймаутов и логи, откатывается на первую версию одним действием, circuit breaker закрывается после успешных вызовов.

### 3.4 Оператор защищается от шумного тенанта

Один мерчант устраивает распродажу, число его чекаутов вырастает в сто раз. Его вызовы упираются в квоту параллельности, часть получает исход `quota_exceeded`, магазин применяет скидку по умолчанию. Латентность вызовов остальных мерчантов не меняется. Оператор в консоли поднимает квоту этому мерчанту, изменение доходит до gateway без перезапуска.

### 3.5 Платформа переживает потерю исполнителя

Под нагрузкой один executor падает. Gateway обнаруживает потерю, кольцо маршрутизации перестраивается, вызовы в полёте повторяются на соседнем executor-е в рамках дедлайна. Соседний executor прогревает модули переехавших тенантов. Магазин не замечает ничего, кроме кратковременного роста латентности, что видно на дашборде.

### 3.6 Разработчик скрипта отлаживается

Разработчик тенанта пишет скрипт на TinyGo, локально собирает и загружает как неактивную версию. В playground вызывает её с произвольным входом, видит выход, логи и длительность. Только после этого активирует. Playground идёт по тому же пути, что боевые вызовы, но не учитывается в квотах и метриках.

## 4. Границы

### 4.1 PoC

Цель: сквозной вертикальный срез и измерения, на основе которых принимаются числовые решения.

- Control plane: оператор, тенанты, хук, загрузка скрипта, валидация через executor, активация. Аутентификация статическим API-ключом. PostgreSQL и MinIO.
- Data plane одним процессом: gateway и executor как два пакета в одном бинарнике, тривиальная маршрутизация. Снимок конфигурации по long-poll: `GET /internal/v1/config/snapshot` с `after_version`/`wait_s`, ответ — полный снимок или 304, не дельты (решение D11, спек M0). Кеш скомпилированных модулей, простой пул инстансов, лимиты времени и памяти, валидация выхода по схеме хука (код тот же, что в Validate).
- Python SDK и демо-магазин на FastAPI с хуком `checkout.discount`. Один скрипт на Rust.
- Docker Compose. Консоли не обязательны, достаточно CLI и curl. Фронт делает каркас консолей.
- Спайк: стоимость инстанцирования из скомпилированного модуля, память на инстанс, число модулей на процесс, размер и холодный старт скрипта на кандидате второго языка. Python исключён как язык скриптов: python-pdk не обновлялся с июня 2025 (решение D15, спек M0); кандидаты — TinyGo и JavaScript. Результат: целевой SLO латентности, размер пула, выбор второго языка для демо.

### 4.2 MVP

Всё из PoC плюс:

- Gateway и executor как отдельные процессы. Consistent hashing по паре «тенант, хук». Discovery через Kubernetes headless service и health-check от gateway. Перестроение кольца при потере executor-а, один повтор вызова на соседе, прогрев модулей по кольцу.
- Квоты тенанта: token bucket по частоте, семафор по параллельности. Admission control с ограниченной очередью на gateway. Circuit breaker на пару «тенант, хук».
- Версии скриптов: активация, откат. Снимок конфигурации по long-poll.
- Валидация списка эффектов по разрешённым типам. Ключ идемпотентности в API и логах.
- Наблюдаемость: метрики Prometheus и дашборд Grafana; логи и метрики на тенанта в консоли.
- Консоль тенанта: хуки, загрузка, версии, активация, playground, логи, метрики. Консоль оператора: хуки, тенанты, квоты, API-ключи.
- Go SDK. Второй язык скрипта по итогам спайка: TinyGo или JavaScript.
- Развёртывание в kind или k3d, Helm-чарт.
- Доказательная база из раздела 14.

### 4.3 Roadmap следующего семестра

Не проектируется детально сейчас, но текущая модель обязана его не блокировать.

- Исполнитель эффектов на стороне платформы: outbox, ретраи, дедупликация по ключу идемпотентности.
- Асинхронные хуки и джобы: очередь, at-least-once, DLQ, упорядочивание.
- KV-хранилище тенанта: чтение через host-функцию, запись как эффект.
- Host-функции чтения, определяемые оператором, с проксированием в его приложение. Декларативное описание потребностей скрипта в данных (по образцу input query в Shopify Functions), которое платформа удовлетворяет до вызова.
- Исходящие HTTP-запросы чтения по allowlist хостов.
- Распределённый лимит частоты вместо приближённого на реплику.
- Сборка скриптов из исходников на стороне платформы.

## 5. Ключевые решения

Каждое решение получит отдельный ADR в `docs/adr`. Здесь резюме с обоснованием.

| # | Решение | Отвергнутые альтернативы | Почему |
|---|---|---|---|
| 1 | Только синхронные хуки в этом семестре | Async сразу; оба | Async ляжет сверху органично: синхронный хук возвращает эффект «поставить джобу». Оба сразу удваивают MVP. |
| 2 | Удалённый сервис плюс тонкий SDK | Sidecar; библиотека в процессе оператора | Только удалённый сервис даёт независимое масштабирование исполнителей, изоляцию отказов и единое место для квот. SDK закрывает эргономику. |
| 3 | Extism поверх wazero, рантайм спрятан за внутренним интерфейсом `sandbox` с контрактным набором тестов `sandboxtest` | Собственный ABI на wazero; Component Model на wasmtime | Extism закрывает обмен данными и даёт PDK для десятка языков. Проверено по исходникам: лимит памяти и прерывание по дедлайну есть. Component Model тянет cgo и нестабильный тулчейн. `go-sdk` не обновлялся с мая 2025 — рантайм спрятан за интерфейсом, а `sandboxtest` делает его замену проверяемой, а не декларативной (решение D7, спек M0; ADR 0003). |
| 4 | Скрипт чистый по построению, эффекты как данные | Разрешить эффекты изнутри исполнения | Повтор вызова безопасен всегда, протокол не нуждается в подтверждении старта и неоднозначных исходах. Индустриальный прецедент: Shopify Functions. |
| 5 | Чтение через host-функции, запись только как эффект | Симметричные host-функции чтения и записи | Чтение делает функцию недетерминированной, но не небезопасной для повтора. Запись как host-функция ломает решение 4. |
| 6 | Политика отказа в точке вызова SDK | Fail-open/fail-closed как свойство хука | Значение по умолчанию знает только оператор в коде. Платформа отдаёт типизированный исход, оператор решает. Одно место вместо двух. |
| 7 | Снимок конфигурации по pull с long-poll | Push от control plane | При push control plane обязан знать состав флота и обрабатывать отказы рассылки, а начальную загрузку всё равно делать pull-ом. Long-poll даёт задержку как у push. |
| 8 | Consistent hashing по паре «тенант, хук» | Любой executor плюс локальный кеш | Локальность тёплого кеша и bulkhead по узлам; при потере узла переезжает только его доля тенантов. |
| 9 | Discovery через Kubernetes headless service | etcd, Consul | Наименьшее, что работает. Отдельный membership-сервис вводится, только если появится потребность, которой нет. |
| 10 | Квоты по wall-clock, без учёта CPU | wasmtime с fuel | wazero не поддерживает fuel. wasmtime требует cgo. Осознанный компромисс, зафиксирован как ограничение. |
| 11 | Валидация модуля выполняется executor-ом по запросу control plane | Валидация в control plane на Python | Правила рантайма живут в одном месте на одном языке. |
| 12 | Python SDK первым, Go SDK в MVP | Go SDK первым | Демо-магазин и SDK делает один человек на одном языке, лид не отвлекается от data plane. Публичный контракт data plane это HTTP/JSON (gRPC только между gateway и executor-ом внутри data plane, решение D6, спек M0), SDK тонкий. |

## 6. Архитектура

### 6.1 Компоненты

**Control plane (Python, FastAPI).**
- API-ключи установки (несколько, именованные, отзывные) вместо аккаунтов операторов, тенанты, пользователи консолей (решение D1, спек M0).
- Реестр хуков.
- Жизненный цикл скриптов: загрузка, хранение в MinIO по content hash, валидация через executor, версии, активация, откат.
- Версионированный снимок конфигурации для data plane; лента изменений (`config_changes`) хранит версию снимка и аудит, data plane читает только полный снимок по long-poll, отдельного эндпоинта дельт нет (решение D11, спек M0).
- Квоты тенантов.
- Проксирование playground-вызовов в gateway с пометкой `test`.
- Выдача консолям логов и метрик из хранилища наблюдаемости.

**Gateway (Go).**
- Единственная точка входа data plane. Аутентификация по API-ключу оператора.
- Держит снимок конфигурации. Проверяет существование хука и активной привязки.
- Квоты тенанта, admission control, circuit breaker.
- Маршрутизация на executor по кольцу, один повтор на соседе.
- Метрики.

**Executor (Go).**
- Держит снимок конфигурации, кеш скомпилированных модулей, пулы инстансов.
- Исполняет вызов с лимитами. Валидирует выход и эффекты.
- Validate-эндпоинт для control plane.
- Прогрев модулей по кольцу. Отправка логов и метрик в хранилище наблюдаемости асинхронно.

**SDK (Python в PoC, Go в MVP).**
- Одна функция вызова хука. Транспорт, дедлайн, повтор при `unavailable` до дедлайна, применение значения по умолчанию.
- Не содержит бизнес-логики. Всё поведение описано на уровне API data plane, чтобы потребитель на любом языке мог ходить напрямую.

**Демо-магазин (Python, FastAPI).** Пример оператора. Хуки `checkout.discount` (PoC) и `order.validate` (MVP). Следует принципу «скрипт решает, хост действует»: скрипт возвращает размер скидки, магазин её применяет. Бэкенд на FastAPI, витрина — route group `(storefront)` в Next.js фронтенда (решение D13, спек M0).

**Консоли (frontend).** Консоль оператора и консоль тенанта, обе ходят только в control plane. Лог вызовов и состояние circuit breaker: в PoC периодический опрос, в MVP — SSE от control plane (решение D12, спек M0).

**Хранилища.** PostgreSQL для control plane и для логов и метрик на тенанта в MVP (замена на ClickHouse в roadmap при необходимости). MinIO для модулей. Prometheus для метрик data plane.

### 6.2 Контракты

**Оператор в gateway.** Публичный транспорт HTTP/JSON (OpenAPI); gRPC используется только для внутренней границы gateway↔executor после их разделения в MVP (решение D6, спек M0). Контракт — `api/invoke.openapi.yaml`, полное описание запроса, ответа и исходов см. спек M0, §6.1. Поля `test` и явный `module_hash` (минуя привязку) для playground — расширение контракта в MVP (§10.3 этого документа), в API M0 их нет.

Заголовок аутентификации содержит API-ключ установки (решение D1, спек M0). `tenant_id` в запросе — это `external_id` тенанта, заданный оператором (решение D2, спек M0); тенанты в data plane не ходят никогда.

**Gateway в executor** (внутренний gRPC в MVP; в M0 это Go-интерфейс в одном процессе, решение D6, спек M0):

```text
Execute(
  tenant_id, hook, hook_def_version, module_hash, config_version,
  payload, deadline_ms, idempotency_key, test
) -> (outcome, output, effects, error, duration_ms, logs при test)

Validate(
  module_hash, hook_def
) -> (ok: bool, report: ValidationReport)
  // executor сам забирает модуль из MinIO по хешу

Health() -> (ok, loaded_modules, pool_stats)
```

`config_version` в `Execute` — часть ключа пула инстансов наравне с `hook_def_version` и `module_hash` (решение D8, спек M0, §11.2).

**Control plane в executor и gateway** (HTTP long-poll):

```text
GET /internal/v1/config/snapshot?after_version=<n>&wait_s=<s>
  -> 200 OK          { version, api_keys, hooks, bindings, tenants } — полный снимок, если его версия больше after_version
  -> 304 Not Modified — по истечении wait_s без изменений
```

Путь и параметры — как в контракте `api/dataplane-internal.openapi.yaml`.

Снимок всегда передаётся целиком (state of the world), не дельтами; отдельного эндпоинта ленты изменений (`/config/changes`) нет (решение D11, спек M0). Клиент при старте забирает полный снимок без `after_version`, затем держит long-poll с последней известной версией.

**Executor в скрипт** (Extism):

- Экспорт скрипта: `handle` для любого хука, вход и выход — байты JSON (решение D10, спек M0).
- Конфиг тенанта передаётся через `config_get` ядра Extism, а не через свою host-функцию (решение D8, спек M0). Логи скрипта — через функции логирования ядра Extism (`log_*`) с лимитом объёма на вызов в обёртке; своей host-функции `log` платформа не заводит (решение D9, спек M0).

### 6.3 Схема выхода и эффекты

Выход скрипта всегда объект:

```json
{
  "result":  { "...": "по схеме выхода хука" },
  "effects": [ { "type": "...", "key": "...", "payload": { } } ]
}
```

Тип эффекта из списка, разрешённого оператором на хуке. В этом семестре платформа только валидирует типы и возвращает список оператору вместе с результатом. Поле `key` служит для дедупликации применения; если скрипт его не задал, executor подставляет ключ идемпотентности вызова плюс порядковый номер эффекта, чтобы два эффекта одного вызова не схлопнулись.

## 7. Модель исполнения

### 7.1 Чистота скрипта

Исполнение скрипта не изменяет мир. Следствия:

- Повтор вызова на другом executor-е безопасен для любого хука.
- Протоколу не нужны подтверждение старта и неоднозначные исходы.
- Скрипт может быть недетерминированным из-за host-функций чтения, это не мешает повтору.

Скрипт теряет только синхронные эффекты изнутри исполнения. Данные извне он получает через вход или через host-функции чтения, разрешённые оператором.

### 7.2 Классификация возможностей

Возможности делятся на два класса, и класс определяется по декларации оператора:

- **Чтение.** Host-функции без изменения мира: лог, конфиг, в roadmap чтение KV, данные оператора, HTTP GET по allowlist. Лог формально пишет, но повтор записи лога безвреден.
- **Эффект.** Всё, что меняет мир. Существует только как тип эффекта в выходе, host-функцией не бывает.

Оператор в хуке перечисляет разрешённые host-функции и разрешённые типы эффектов. Control plane при валидации проверяет, что импорты модуля входят в разрешённый список. Executor при каждом вызове проверяет, что типы эффектов в выходе входят в разрешённый список, иначе исход `handler_error`.

Платформа не может проверить, что внешний сервис по HTTP GET ничего не меняет. Классификация host-функции как чтения это декларация и ответственность оператора.

### 7.3 Ключ идемпотентности

Оператор передаёт его в вызове, например идентификатор заказа плюс имя хука. В этом семестре ключ попадает в логи вызова и в поле `key` эффектов. В roadmap им пользуется исполнитель эффектов для дедупликации.

## 8. Горячий путь вызова

Топология MVP. В PoC gateway и executor это один процесс, шаги те же.

1. **SDK.** Формирует запрос с дедлайном и ключом, отправляет в gateway. При `unavailable` повторяет, пока позволяет дедлайн.
2. **Gateway, допуск.** API-ключ определяет оператора. По снимку: хук существует, иначе `404` (решение D4, спек M0). Вход проверяется по схеме входа хука, ошибка — `400` (решение D5, спек M0). У тенанта есть активная привязка, иначе `no_handler` без обращения к executor-у; так же для незарегистрированного тенанта — оператору не нужно знать, кто из тенантов что загрузил (решение D3, спек M0). Token bucket тенанта, иначе `quota_exceeded`. Семафор параллельности тенанта, при исчерпании ожидание в ограниченной очереди до дедлайна, затем `quota_exceeded`. Общий admission control: при переполнении очереди gateway немедленный `unavailable`. Circuit breaker пары «тенант, хук» в открытом состоянии: немедленный исход последнего типа отказа.
3. **Gateway, маршрутизация.** Ключ кольца хеш от `tenant_id` и `hook`. Execute на выбранный executor с `module_hash` и `hook_def_version`.
4. **Executor, исполнение.** Скомпилированный модуль из кеша по ключу «module_hash, hook_def_version» (набор линкуемых host-функций зависит от определения хука). При промахе загрузка из MinIO по хешу, компиляция, помещение в кеш. Инстанс из пула пары «тенант, модуль»; при отсутствии свободного и достижении лимита пула короткое ожидание в ограниченной очереди пула, затем `unavailable`. В штатном режиме до этого не доходит: квота параллельности на gateway меньше или равна размеру пула, насыщение возможно только во время перестроения кольца. Вызов с дедлайном, равным минимуму остатка дедлайна запроса и лимита хука. Лимит памяти из определения хука. Выход проверяется по схеме, эффекты по разрешённым типам.
5. **Executor, после вызова.** Здоровый инстанс возвращается в пул. После таймаута, трапа или превышения памяти инстанс закрывается и выбрасывается: wazero закрывает модуль при отмене контекста, инстанс мёртв по факту. Плановая переработка после N вызовов, чтобы куча гостя не росла. Запись о вызове (тенант, хук, версия, исход, длительность, ключ, логи, `test`) уходит в буферизованный канал, асинхронно пишется в хранилище наблюдаемости. При переполнении канала запись отбрасывается, счётчик потерь растёт. Горячий путь на наблюдаемости не блокируется.
6. **Gateway, ответ.** При обрыве соединения с executor-ом или его ошибке уровня транспорта один повтор на следующем узле кольца, если остаток дедлайна больше порога. Иначе `unavailable`. Исход и метрики.
7. **SDK, результат.** При `ok` результат и эффекты. При любом другом исходе и заданном значении по умолчанию значение с пометкой `fallback=true` и исходом. Без значения по умолчанию исключение с исходом.

Бюджет латентности и целевой SLO фиксируются после спайка. До измерения числа в документе отсутствуют намеренно.

## 9. Отказы и деградация

| Отказ | Обнаружение | Поведение | Что видит оператор |
|---|---|---|---|
| Скрипт завис | Дедлайн вызова | Инстанс закрыт и выброшен, вызов учтён тенанту, breaker считает отказ | `timeout` |
| Скрипт упал, трап, превышение памяти | Ошибка вызова | То же | `handler_error` |
| Серия отказов пары «тенант, хук» | Circuit breaker, окно и порог настраиваются | Быстрый отказ без обращения к executor-у на время cooldown, затем полуоткрытое состояние | Тот же исход, мгновенно |
| Executor умер | Health-check gateway, обрыв соединения | Кольцо перестраивается, вызовы в полёте повторяются на соседе, сосед прогревает переехавшие модули | Кратковременный рост латентности; `unavailable` для вызовов, у которых дедлайн не оставил места для повтора |
| Пул тенанта насыщен (перестроение кольца) | Очередь пула полна | `unavailable` для части вызовов этого тенанта, gateway повторяет на соседе, остальные тенанты в своих пулах | `unavailable`, не `timeout`: скрипт не запускался |
| Gateway умер | Балансировщик | Реплики stateless относительно запросов. Состояние квот и breaker-ов в памяти реплики, лимиты приближённые | Ничего |
| Control plane недоступен | Long-poll не отвечает | Data plane работает по последнему снимку, изменения не доходят, консоли недоступны | Ничего на вызовах |
| MinIO недоступен | Ошибка загрузки модуля | Закешированные модули работают, холодные промахи `unavailable` | `unavailable` для новых привязок |
| Перегрузка gateway | Очередь admission control полна | Немедленный `unavailable`, латентность принятых вызовов не растёт | `unavailable` |
| Смена версии | Дельта снимка | Короткое окно, когда разные executor-ы исполняют разные версии. Допустимо | `module_hash` в ответе |
| Шумный тенант | Квоты | Упирается в свой token bucket и семафор, остальные не затронуты | `quota_exceeded` у одного тенанта |

## 10. Control plane

### 10.1 Модель данных

- `api_keys`: id, name, sha256, created_at, revoked_at. Заменяет `operators`: одна установка обслуживает одного оператора, ключи принадлежат установке, а не аккаунту (решение D1, спек M0).
- `tenants`: id, external_id (уникален в пределах установки), name, rate_limit_rps, concurrency_limit, status. `operator_id` удалён вместе с `operators` (решения D1, D2, спек M0).
- `hooks`: id, name, def_version, input_schema, output_schema, timeout_ms, memory_max_pages, allowed_host_functions[], allowed_effect_types[], sample_input. `operator_id` удалён по той же причине (решение D1, спек M0).
- `modules`: id, tenant_id, hook_id, content_hash, size_bytes, status (`uploaded`, `validating`, `validated`, `rejected`, `archived`), validation_report, uploaded_at. Статусы без изменений: «активна» — свойство `bindings`, а не `modules` (решение D14, спек M0; уже соответствует).
- `bindings`: tenant_id, hook_id, active_module_id (nullable), tenant_config (JSON), config_version, updated_at. `config_version` — часть ключа пула инстансов (решение D8, спек M0, §11.2).
- `config_changes`: seq, kind, payload, created_at. Версия снимка и аудит изменений; data plane потребляет только полный снимок по long-poll, отдельной ленты дельт data plane не читает (решение D11, спек M0).
- `invocations` (наблюдаемость, MVP): tenant_id, hook, module_hash, outcome, duration_ms, idempotency_key, test, logs (ограниченный текст), executor_id, ts. Партиционирование по времени, TTL.

Каждое изменение хука увеличивает `def_version`. Каждое изменение хуков, привязок и квот добавляет запись в `config_changes` и увеличивает версию снимка.

### 10.2 Жизненный цикл скрипта

1. Тенант загружает файл. Control plane проверяет лимит размера, считает content hash, складывает в MinIO, создаёт `modules` со статусом `uploaded`.
2. Control plane вызывает Validate на любом executor-е. Executor: загружает модуль, компилирует, проверяет наличие экспорта с именем хука, проверяет, что импорты входят в `allowed_host_functions` плюс служебные импорты Extism и, если этого требует PDK, WASI без доступа к файловой системе и окружению. Инстанцирует с лимитами хука, вызывает на `sample_input`, проверяет выход по схеме. Возвращает отчёт.
3. Статус `validated` или `rejected` с отчётом.
4. Тенант активирует версию: `bindings.active_module_id` меняется, запись в `config_changes`. Предыдущая версия остаётся, откат это активация предыдущей.
5. Архивация неактивных версий по желанию тенанта.

Валидация не гарантирует корректность на всех входах, это показывает user story 3.3. Гарантирует только соответствие контракту хука и capability-модели.

**Изменение хука после привязки.** Списки `allowed_host_functions` и `allowed_effect_types` в этом семестре только расширяются: удаление возможности, которую уже импортирует активный скрипт, control plane отклоняет. Изменение схем или лимитов запускает повторную валидацию всех привязанных модулей этого хука в фоне; провалившие её остаются активными, но помечаются в консоли тенанта как несовместимые. Оператора на горячем пути защищает валидация выхода: несовместимый скрипт даёт `handler_error`, а не мусор. Автоматическая деактивация в roadmap.

### 10.3 Playground

Консоль тенанта отправляет вход и выбранную версию в control plane. Control plane вызывает gateway по внутренним учётным данным с `test=true` и явным `module_hash`, минуя привязку. Флаг `test` с ключом оператора отклоняется. Gateway не применяет квоты и не считает метрики для `test`, executor пишет запись с пометкой `test` и дополнительно возвращает логи в ответе, чтобы консоль показала их сразу, не дожидаясь асинхронной записи. Так тестовый вызов идёт тем же путём, что боевой.

## 11. Data plane, детали

### 11.1 Кольцо и discovery

- Gateway резолвит headless service executor-ов, получает адреса, строит кольцо с виртуальными узлами.
- Health-check каждого executor-а с интервалом. Узел убирается из кольца после K подряд неудач, возвращается после успеха.
- Ключ кольца: хеш от `tenant_id` и `hook`. Повтор идёт на следующий узел по кольцу.
- Executor резолвит тот же headless service, узнаёт свои пары по тому же алгоритму (та же библиотека, тот же список узлов) и прогревает их модули при старте и при изменении списка. Расхождение взглядов gateway и executor-а на кольцо во время перестроения допустимо: прогрев это оптимизация, не корректность.

### 11.2 Кеш модулей и пул инстансов

- Кеш скомпилированных модулей: LRU по ключу «module_hash, hook_def_version», лимит по числу или объёму. Кеш компиляции wazero включён. Скомпилированный модуль не несёт состояния, поэтому два тенанта с побайтово одинаковым wasm (например, немодифицированный шаблон) разделяют компиляцию.
- Пул инстансов по ключу «tenant_id, hook, hook_def_version, module_hash, config_version»: изменение конфига тенанта естественно порождает новый пул, старый вымирает по простою (решение D8, спек M0). Инстансы никогда не разделяются между тенантами, даже при одинаковом модуле: куча гостя сохраняется между вызовами, и общий инстанс означал бы утечку состояния одного тенанта в вызовы другого. Пул ограничен сверху значением, выводимым из квоты параллельности тенанта. Инстанс закрывается после таймаута или трапа, после N вызовов, по простою.
- Инстанс не потокобезопасен, один вызов за раз, это гарантирует пул.
- Extism между вызовами сбрасывает только свою служебную память, куча гостя сохраняется. Внутри одного тенанта это допустимо, рост кучи ограничивается переработкой инстанса.

### 11.3 Лимиты

- Память: `memory_max_pages` из определения хука в манифест Extism.
- Время: `timeout_ms` хука в манифест, чтобы включился режим закрытия по контексту, плюс контекст с дедлайном на каждый вызов.
- Host-функции, которые сами могут блокироваться (в roadmap чтение KV, HTTP), обязаны уважать контекст вызова.
- Квоты частоты и параллельности на gateway, на реплику. Ограничение задокументировано.

### 11.4 Наблюдаемость

- Метрики Prometheus на gateway и executor: вызовы по исходам, латентность по хуку и тенанту, размер очередей, состояние breaker-ов, размер пулов, промахи кеша, потери записей наблюдаемости.
- Записи о вызовах с логами в PostgreSQL через буферизованный канал и батчи. Лог на вызов ограничен по объёму, лишнее обрезается с пометкой.
- Дашборд Grafana для защиты: латентность против числа executor-ов, момент убийства узла, шумный тенант.

## 12. Безопасность и изоляция

- Изоляция памяти и отсутствие доступа к системе за счёт wasm. WASI включается только если этого требует PDK, и тогда без монтирования файловой системы, без переменных окружения, без сети.
- Скрипт получает только host-функции из `allowed_host_functions` хука. Импорт чего-либо иного отклоняется на валидации.
- Лимиты памяти и времени на каждый инстанс.
- Тенанты не имеют доступа к data plane. Оператор аутентифицируется API-ключом, ключ хранится хешированным.
- Модули адресуются по content hash, подмена в хранилище обнаруживается при загрузке.
- Лог на вызов ограничен, чтобы скрипт не мог забить хранилище.
- Не защищаемся в этом семестре: side-channel атаки между тенантами на одном узле, точный учёт CPU.

## 13. Развёртывание

- **Разработка.** Docker Compose: PostgreSQL, MinIO, control plane, data plane одним процессом (PoC) или gateway плюс executor (MVP), демо-магазин, Prometheus, Grafana.
- **MVP и защита.** kind или k3d. Helm-чарт: control plane, gateway с несколькими репликами, executor как Deployment с headless service, PostgreSQL и MinIO как зависимости чарта для демо.
- **Self-hosted упаковка.** Helm-чарт и есть продукт для оператора.

## 14. Доказательная база и тестирование

### 14.1 Артефакты

- ADR на каждое решение из раздела 5 в `docs/adr`, с отвергнутыми альтернативами.
- Диаграммы C4: context и container. Sequence-диаграмма горячего пути. Диаграмма отказов из раздела 9.
- Нагрузочные сценарии на k6:
  - Латентность p50 и p99 против числа executor-ов при фиксированной нагрузке. Ожидание: близкая к линейной масштабируемость пропускной способности.
  - Шумный тенант: один тенант превышает квоту в разы, латентность остальных не меняется.
  - Убийство executor-а под нагрузкой: всплеск `unavailable` и латентности, время восстановления кольца.
  - Холодный старт: латентность первого вызова после переезда тенанта.
- Живое демо на защите: магазин под нагрузкой, убивается pod executor-а, скидки продолжают считаться.

### 14.2 Тесты

- **Unit.** Пул инстансов, кольцо и его перестроение, token bucket, семафор, circuit breaker, валидация выхода и эффектов, разбор снимка конфигурации.
- **Интеграционные.** Executor с настоящими wasm-модулями: лимит памяти, таймаут с бесконечным циклом, трап, переиспользование инстанса, выброс после таймаута, Validate с неразрешённым импортом, два тенанта с одинаковым модулем не разделяют инстанс и не видят состояние друг друга.
- **E2E.** Compose, сквозной сценарий: создать хук, загрузить скрипт, активировать, вызвать через SDK, откатить.
- **Отказы.** Скриптованные сценарии из раздела 9 против kind: убить executor, остановить control plane, остановить MinIO.

## 16. Спайк перед PoC

Вопросы, без ответа на которые числовые решения не принимаются:

1. Стоимость создания инстанса из скомпилированного модуля Extism и потребление памяти на инстанс. Определяет размер пула и то, нужен ли тёплый пул вообще.
