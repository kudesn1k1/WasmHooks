# Milestone 1: фундамент control plane и подключение data plane

Design-спецификация вехи. Дата: 2026-10-09. Контрольная точка: ~2026-10-16.

Основной спек: `2026-09-04-wasm-extension-platform-design.md`. Спек M0: `2026-09-24-milestone-0-design.md`. Этот документ детализирует PoC (основной спек §4.1) для M1 и фиксирует решения, принятые 09.10. Где документы расходятся, прав этот.

---

## 1. Цель

Дать control plane родиться и подключить к нему data plane: изменение конфигурации в control plane доходит до data plane без перезапуска, а отказ control plane не останавливает вызовы. Заложить фундамент control plane так, чтобы backend-разработчик в день открытия PR знал, что делать, и мог начать по образцу.

Две аудитории результата:

- **Тимлид** защищает архитектуру перед преподавателем: демо доказывает утверждения §9 основного спека, разбор вехи объясняет, что и почему построено.
- **Backend-разработчик** получает работающий каркас, эталонный срез для копирования, контракт консолей и упорядоченный список задач с критериями приёмки.

## 2. Definition of Done

Каждый пункт проверяется человеком за несколько минут.

### Обязательно

1. **Фундамент `control-plane/`.** Каркас по разделу 6.1, полная модель данных раздела 6.2 одной миграцией, эндпоинт снимка с long-poll (раздел 6.4), аутентификация (раздел 6.5), эталонный срез «хуки оператора» (раздел 6.6). Тесты на настоящем PostgreSQL зелёные, в CI есть джоба `control-plane`.
2. **Data plane забирает снимок из control plane.** `HTTPSource` с long-poll и бэкоффом (раздел 7.1); при отказе control plane data plane держит последний снимок и обслуживает вызовы. Режим M0 (`-snapshot` файлом) работает как раньше, `go run ./cmd/demo` проходит.
3. **Compose.** `docker compose up` в корне поднимает PostgreSQL, MinIO, control plane и data plane (раздел 8.1).
4. **Демо, доказывающее утверждения архитектуры.** `go run ./e2e/cmd/demo` против поднятого compose печатает таблицу (раздел 8.2):
   - хук, созданный через API control plane, становится виден data plane без перезапуска: вызов меняется с `404` на `no_handler`, время распространения не больше 1 с;
   - после `docker compose stop control-plane` вызовы продолжают обслуживаться по последнему снимку;
   - после `docker compose start control-plane` data plane подхватывает следующее изменение.
5. **Контракт консолей.** Роутеры-заглушки с pydantic-схемами для всех эндпоинтов PoC (раздел 6.7), формы взяты из MSW-моков фронтенда. Из кода сгенерирован `api/control-plane.openapi.yaml`, CI падает при расхождении файла и кода. Фронтенд-разработчик в ревьюерах PR.
6. **Передача задач backend-разработчику.** `docs/handoff/backend.md` по разделу 10: картина целиком, user stories, как запустить, разбор эталонного среза, правила, задачи T1–T8 по порядку с критериями приёмки. `docs/TEAM.md` дополнен разделом M1.
7. **Разбор вехи для тимлида** (диаграммы первыми, Python через контракты и аналоги из Go), разбивка состава каждого PR, отчёт о делегировании. CI зелёный на самих PR. Основной спек получает ссылки на решения раздела 3 в затронутых разделах.

### Желательно

- **`modstore.S3`** (раздел 7.2) и **эндпоинт Validate** на внутреннем порту (раздел 7.3).
- **Dev-only seed** (раздел 6.8): кладёт `discount.wasm` в MinIO, валидирует через data plane, создаёт тенанта, модуль и привязку. Демо дополнительно показывает `ok` с модулем, скачанным из MinIO по хешу, и отчёт Validate для хорошего модуля и модуля с запрещённым импортом. Seed подписан как seed, а не как поток загрузки: поток загрузки — задачи T3–T5.

### Stretch

- **S7b: ограничение одновременно исполняемых вызовов** (раздел 11). Отдельный PR, только после зелёного DoD; иначе первый пункт M2. Случаи N < ядер в бенчмарке S7b можно добавить в любом случае.

### Не входит в M1

Не реализуется даже частично: квоты тенанта и admission control на gateway (поля квот есть в модели и снимке, data plane их не применяет), circuit breaker, кольцо, discovery, разделение gateway и executor, gRPC, playground и флаг `test`, SSE, хранилище вызовов (`invocations`) и эндпоинт `/tenant/invocations`, реализация эндпоинтов T1–T8 (это работа backend-разработчика), Python SDK, демо-магазин, форк go-sdk Extism, взвешенный лимит инстансов, замер RSS, второй язык скриптов, повторная валидация модулей при изменении хука, удаление хуков, Kubernetes и Helm.

## 4. User stories M1

### 4.1 Оператор разворачивает платформу и создаёт хук

Разработчик магазина выполняет `docker compose up`. Создаёт первый ключ установки командой `docker compose exec control-plane controlplane apikey create --name shop` и сохраняет показанное значение: второй раз его не покажут. Вызывает хук `checkout.discount` для `merchant-a` и получает `404`: такого хука нет. Создаёт хук через `POST /api/v1/hooks` с ключом. Меньше чем через секунду тот же вызов возвращает `no_handler`: хук есть, скрипта у тенанта нет, магазин применяет скидку по умолчанию. Data plane никто не перезапускал.

### 4.2 Control plane падает, магазин не замечает

Control plane останавливается. Data plane получает ошибки long-poll, повторяет запросы с бэкоффом и обслуживает вызовы по последнему снимку. Консоли недоступны, вызовы проходят. Control plane возвращается, следующее изменение хука доходит до data plane.

### 4.3 Мерчант открывает консоль из магазина

Мерчант нажимает в магазине «Мои скрипты». Бэкенд магазина с ключом установки вызывает `POST /api/v1/tenants/merchant-a/console-sessions` и получает токен на час. Консоль тенанта ходит в control plane с этим токеном и видит только хуки и модули `merchant-a`. В M1 готовы выдача токена и его проверка; эндпоинты консоли тенанта реализует backend-разработчик (T3–T6).

### 4.4 Backend-разработчик начинает работу

Backend-разработчик открывает `docs/handoff/backend.md`: картина на одной странице, его зона, порядок задач. Поднимает compose, запускает `uv run pytest`. Читает папку `controlplane/hooks/`, разобранную в документе по шагам, и делает задачу T1 (тенанты) по её образцу: роутер, сервис, репозиторий, вызов `bump_config_version`, тесты. Критерии приёмки T1 говорят, какие тесты должны появиться. CI подтверждает.

### 4.5 Модуль из MinIO (желательно)

`controlplane seed-demo` кладёт `discount.wasm` в MinIO, отправляет его на Validate, получает отчёт `ok`, создаёт тенанта `merchant-a`, модуль и привязку. Data plane получает снимок с привязкой, скачивает модуль из MinIO по хешу, проверяет хеш и компилирует. Вызов `merchant-a` возвращает `ok` со скидкой. Тот же Validate для `http-call.wasm` возвращает отчёт с проваленной проверкой `imports`.

## 5. Архитектура M1

```text
                 ┌────────────────────────── docker compose ──────────────────────────┐
 оператор ─────► │ control-plane :8000 (FastAPI)                                      │
 (curl, CLI)     │   /api/v1/...          API оператора    (ключ установки)           │
 тенант ───────► │   /api/v1/tenant/...   API консоли тенанта (JWT тенанта)           │
                 │   /internal/v1/config/snapshot   (внутренний токен) ◄────────┐     │
                 │        │ SQL                     │ S3 PUT                    │     │
                 │        ▼                         ▼                           │     │
                 │   PostgreSQL                MinIO  bucket modules            │     │
                 │                                  ▲ S3 GET по хешу           │     │
                 │ dataplane (Go, один процесс)     │                           │     │
                 │   :8080 публичный   /v1/invoke ◄──── магазин, curl            │     │
                 │   :8081 внутренний  /internal/v1/modules/validate ◄── CP      │     │
                 │   HTTPSource: long-poll снимка ───────────────────────────────┘     │
                 └────────────────────────────────────────────────────────────────────┘
```

**Изменение конфигурации.** Оператор меняет хук через API. В одной транзакции: строки изменения, увеличение версии под блокировкой строки `config_state`, запись в `config_changes`; коммит. `VersionWatcher` замечает новую версию не позже чем через интервал опроса и будит ждущие запросы. Они получают 200 с полным снимком, сериализованным один раз на версию. Data plane разбирает снимок, применяет через `Store.Update` (принимается только строго более новая версия) и в фоне компилирует модули новых привязок.

**Модуль.** Загрузка (T3) считает sha256 и кладёт байты в MinIO по ключу `<hex>.wasm`, как у `modstore.FS`. Оркестрация (T4) вызывает Validate: data plane забирает модуль из MinIO, проверяет хеш, компилирует, проверяет экспорты и импорты, делает пробный вызов на `sample_input`. Активация (T5) меняет привязку, дальше как при изменении конфигурации.

**Отказ control plane.** Long-poll получает ошибки, data plane повторяет с экспоненциальным бэкоффом и держит последний снимок. Если control plane недоступен при старте data plane, процесс поднимается, но `readyz` отвечает 503 до первого снимка.

## 6. Control plane

### 6.1 Структура и стек

```text
control-plane/
  pyproject.toml, uv.lock, alembic.ini, Dockerfile
  migrations/versions/0001_initial.py
  src/controlplane/
    app.py            create_app(): единственное место, где собираются зависимости
    settings.py       настройки из env с префиксом CP_
    db.py             движок, фабрика сессий, хелпер транзакции
    errors.py         ошибки в application/problem+json (RFC 9457)
    cli.py            apikey create, openapi, seed-demo, validate-module
    auth/             ключ установки, JWT тенанта, внутренний токен
    configstate/      bump_config_version, VersionWatcher, сборка снимка, эндпоинт снимка
    hooks/            эталонный срез: router.py, service.py, repo.py, schemas.py
    tenants/ apikeys/ modules/ bindings/ tenantconsole/   заглушки 501 со схемами
    storage/          put/get модуля в S3 по хешу
    dpclient/         клиент Validate data plane
  tests/
```

Стек — решение D24. Стиль: запросы через явный `select()`, без ленивых связей ORM; транзакции видны в коде (`async with session.begin()`); репозитории возвращают простые структуры; зависимости собираются в `app.py`, обработчики получают уже собранные сервисы.

Настройки (env): `CP_DATABASE_URL`, `CP_INTERNAL_TOKEN`, `CP_TENANT_JWT_SECRET`, `CP_TENANT_TOKEN_TTL_S` (3600), `CP_SNAPSHOT_POLL_INTERVAL_S` (0.5), `CP_S3_ENDPOINT`, `CP_S3_BUCKET`, `CP_S3_ACCESS_KEY`, `CP_S3_SECRET_KEY`, `CP_DATAPLANE_INTERNAL_URL`, `CP_MAX_MODULE_BYTES` (10 МиБ, для T3).

### 6.2 Модель данных

| Таблица | Поля | Ограничения |
|---|---|---|
| `config_state` | `id` (всегда 1), `version` | Одна строка, создаётся миграцией с `version = 1`. |
| `config_changes` | `version` PK, `kind`, `payload` jsonb, `created_at` | Аудит изменений. `version` берётся из `config_state`. |
| `api_keys` | `id` (`key_…`), `name`, `sha256`, `created_at`, `revoked_at` | `name` и `sha256` уникальны; `sha256` — 64 символа `[0-9a-f]`. |
| `tenants` | `id` uuid, `external_id`, `name`, `rate_limit_rps`, `concurrency_limit`, `created_at`, `updated_at` | `external_id` уникален и непуст; лимиты ≥ 0 (0 — значение по умолчанию data plane). |
| `hooks` | `id` uuid, `name`, `def_version`, `input_schema`, `output_schema`, `timeout_ms`, `memory_max_pages`, `allowed_host_functions` text[], `allowed_effect_types` text[], `sample_input`, `created_at`, `updated_at` | `name` уникален и соответствует `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$`; `def_version ≥ 1`; `timeout_ms` в [1, 30000]; `memory_max_pages` в [16, 16384]; схемы — JSON-объекты. |
| `modules` | `id` uuid, `tenant_id`, `hook_id`, `content_hash`, `size_bytes`, `status`, `validation_report` jsonb, `uploaded_at` | `content_hash` соответствует `^sha256:[0-9a-f]{64}$`; `status` из D14; уникальны `(tenant_id, hook_id, content_hash)` и `(id, tenant_id, hook_id)`. |
| `bindings` | `tenant_id`, `hook_id` (PK пары), `active_module_id`, `config` jsonb, `config_version`, `updated_at` | Составной FK `(active_module_id, tenant_id, hook_id)` → `modules(id, tenant_id, hook_id)`: активировать модуль чужого тенанта или другого хука нельзя на уровне БД. `config` — объект со строковыми значениями; `config_version ≥ 1`. |

Таблицы `invocations` в M1 нет. Поле `tenants.status` из основного спека не вводится, пока у него нет определённой семантики.

**Соответствие `config.validate` (D22).** Уникальность хуков, тенантов и привязок, границы `timeout_ms` и `memory_max_pages`, формат хешей, ссылки привязок на существующие хук и тенанта, `version ≥ 1` гарантируются ограничениями БД, а не только кодом сервисов.

### 6.3 Путь записи и версия снимка

`configstate.bump_config_version(session, kind, payload) -> int` выполняется внутри транзакции вызывающего: `UPDATE config_state SET version = version + 1 WHERE id = 1 RETURNING version`, затем вставка в `config_changes`. Блокировка строки держится до коммита, поэтому версии выдаются в порядке коммитов.

Правило: каждая операция, меняющая видимое в снимке, вызывает `bump_config_version` ровно один раз. Видимое в снимке — хуки, тенанты (включая квоты), привязки, ключи установки. Загрузка модуля и смена его статуса версию не двигают. Изменение определения хука увеличивает `def_version`; изменение конфига привязки увеличивает `config_version`; активация другого модуля `config_version` не меняет (`module_hash` и так входит в ключ пула).

### 6.4 Эндпоинт снимка

`GET /internal/v1/config/snapshot` по `api/dataplane-internal.openapi.yaml`, внутренний токен.

- Без `after_version` или при `after_version` меньше текущей версии — сразу 200 с текущим снимком.
- Иначе ожидание на `VersionWatcher` до `wait_s` (1–60, по умолчанию 30): 200, как только версия превысила `after_version`, или 304 по истечении времени.
- Некорректные параметры — 400 в формате problem+json.
- Сборка: одна транзакция `REPEATABLE READ READ ONLY` читает версию и все таблицы. В снимок попадают неотозванные ключи, все хуки и тенанты, привязки с активным модулем (хеш берётся из `modules`).
- Сериализованные байты кешируются для последней версии; одновременные сборки одной версии склеиваются (single-flight).

`VersionWatcher`: фоновая задача раз в `CP_SNAPSHOT_POLL_INTERVAL_S` читает `config_state.version`. При росте версии сохраняет её и будит всех ждущих (`asyncio.Event.set()` и замена на новый event, аналог `close(ch)` в Go). Интерфейс: `current() -> int`, `wait_newer(after, timeout) -> bool`.

### 6.5 Аутентификация

- **Ключ установки** (D19). Значение `whk_` + 32 случайных символа base62, показывается один раз при создании; в БД sha256. Зависимость `require_operator` ищет неотозванный ключ по хешу. Эти же ключи попадают в снимок и аутентифицируют вызовы `Invoke`.
- **JWT тенанта** (D18). HS256, секрет `CP_TENANT_JWT_SECRET`. Claims: `sub` = `external_id`, `aud` = `tenant-console`, `iss` = `wasmhooks-control-plane`, `iat`, `exp` (`CP_TENANT_TOKEN_TTL_S`). `POST /api/v1/tenants/{external_id}/console-sessions` (ключ установки) возвращает `{token, expires_at}`; несуществующий тенант — 404. Зависимость `require_tenant` проверяет подпись, `aud` и срок без обращения к БД и отдаёт `external_id`.
- **Внутренний токен** на `/internal/*`: сравнение за постоянное время с `CP_INTERNAL_TOKEN`.
- Ошибки: 401 problem+json без уточнения, что именно не так.

### 6.6 Эталонный срез: хуки оператора

| Метод и путь | Поведение |
|---|---|
| `GET /api/v1/hooks` | Список хуков `{items: [...]}`. |
| `POST /api/v1/hooks` | Создание. 201; 409, если имя занято. `def_version = 1`, версия снимка +1. |
| `GET /api/v1/hooks/{name}` | Определение хука; 404, если нет. |
| `PUT /api/v1/hooks/{name}` | Полная замена определения (имя неизменно). Если определение не изменилось — 200 без увеличения версий. Иначе `def_version + 1` и версия снимка +1. Удаление элемента из `allowed_host_functions` или `allowed_effect_types` — 409 (консервативная форма правила §10.2 основного спека: списки только растут). |

Проверки при создании и замене: `input_schema` и `output_schema` — корректные JSON Schema draft 2020-12; `sample_input` проходит `input_schema`; лимиты в границах раздела 6.2. Ошибки проверки — 422 problem+json с указанием поля.

Срез показывает весь паттерн: схемы запроса и ответа, роутер без логики, сервис с транзакцией и вызовом `bump_config_version`, репозиторий на явных запросах, ошибки problem+json, тесты на настоящем PostgreSQL. Повторная валидация привязанных модулей при изменении схем и лимитов в M1 не делается (раздел 14).

### 6.7 Контракт консолей и заглушки

Заглушки отвечают 501 problem+json, но имеют полные схемы запроса и ответа, поэтому попадают в `api/control-plane.openapi.yaml` в окончательном виде.

| Группа | Эндпоинты | Задача |
|---|---|---|
| Тенанты | `GET/POST /api/v1/tenants`, `GET/PATCH /api/v1/tenants/{external_id}` | T1 |
| Ключи установки | `GET/POST /api/v1/api-keys`, `DELETE /api/v1/api-keys/{id}` (отзыв) | T2 |
| Консоль тенанта | `GET /api/v1/tenant/hooks`, `GET /api/v1/tenant/hooks/{hook}`, `GET/POST /api/v1/tenant/hooks/{hook}/modules`, `PUT /api/v1/tenant/hooks/{hook}/binding` | T3–T6 |

Формы консоли тенанта повторяют `web/src/mocks/handlers.ts` и zod-схемы `web/src/entities/*/model/schema.ts` поле в поле. ## 7. Data plane

### 7.1 `HTTPSource` и цикл обновления

Новый тип в пакете `config`:

- первый запрос без `after_version`, дальше `GET <cp>/internal/v1/config/snapshot?after_version=<v>&wait_s=30` с внутренним токеном, таймаут клиента `wait_s + 10 с`;
- 200 → `Parse` → `Store.Update`; `ErrStaleSnapshot` игнорируется; ошибка разбора логируется и ведёт к бэкоффу (иначе control plane немедленно отдавал бы тот же снимок по кругу);
- 304 → следующий запрос сразу;
- ошибка транспорта или статус 5xx → экспоненциальный бэкофф от 0.5 до 10 с с full jitter, сброс после успеха;
- после каждого применённого снимка — фоновый `Executor.Preload`; одновременно идёт не больше одного прогона, при наложении следующий прогон выполняется один раз с последним снимком.

`cmd/dataplane`: при `-control-plane-url` до первого снимка `readyz` отвечает 503, первый снимок проходит предзагрузку до перехода в ready, как в M0. Флаги `-snapshot` и `-control-plane-url` взаимоисключающие.

### 7.2 `modstore.S3`

Реализация `modstore.Store` на minio-go v7: ключ `<hex>.wasm` в бакете, проверка хеша, `ErrNotFound` при отсутствии объекта, `ErrHashMismatch` при несовпадении. Табличный набор тестов поведения `Store` общий для `FS` и `S3`; `S3` проверяется против MinIO в testcontainers-go. Флаги `-s3-endpoint`, `-s3-bucket`, `-s3-region`, `-s3-insecure`; ключи доступа из env `WASMHOOKS_S3_ACCESS_KEY`, `WASMHOOKS_S3_SECRET_KEY`. `-modules-dir` и `-s3-endpoint` взаимоисключающие.

### 7.3 Validate

`Executor.Validate(ctx, moduleHash, hook, config) (ValidationReport, error)`. Проверки по порядку контракта; после первой проваленной остальные получают `ok: false, detail: "skipped"`:

| Проверка | Что делает | Провал |
|---|---|---|
| `fetch` | `modstore.Get` по хешу | Модуля нет или хеш не совпал. Временная ошибка хранилища — не провал проверки, а ответ 503: control plane повторит позже, модуль останется `validating`. |
| `compile` | Компиляция с лимитами хука, **без** помещения в кеш модулей | Ошибка рантайма. |
| `exports` | Есть экспорт `handle` | Нет экспорта. |
| `imports` | Импорты входят в разрешённые (спек M0 §7.2) | Запрещённый импорт, в `detail` его имя. |
| `sample_call` | Одноразовый инстанс, вход `sample_input`, конфиг из запроса или пустой, дедлайн `timeout_ms` хука; выход проверяется по `output_schema`, эффекты по `allowed_effect_types` | Любой исход, кроме `ok`; в `detail` исход и ошибка. |

Проверки экспортов и импортов выполняются внутри `sandbox.Runtime.Compile` (спек M0 §7.2), поэтому Validate вызывает тот же `Compile`, что и горячий путь, но напрямую, мимо кеша executor, и раскладывает ошибку по проверкам. Для этого `sandbox` получает типизированные ошибки `ErrMissingExport` и `ErrForbiddenImport`, обёртки `ErrInvalidModule`:

- запрещённый импорт → `compile` и `exports` ok, `imports` провал (как в примере контракта);
- нет `handle` или неверная сигнатура → `compile` ok, `exports` провал;
- прочий `ErrInvalidModule` → `compile` провал;
- ошибка платформы при компиляции (не модуля) → ответ 503.

Отчёт всегда содержит все пять проверок в порядке контракта. Скомпилированный модуль и инстанс закрываются после проверки. Одновременно выполняется не больше `-validate-concurrency` валидаций (по умолчанию 1), остальные ждут в пределах контекста запроса.

**Изменение контракта** `api/dataplane-internal.openapi.yaml` (добавляющее, отдельным коммитом до кода): необязательное поле `config` в запросе Validate (объект строк) и ответ 503 при временной недоступности хранилища модулей.

### 7.4 Внутренний порт, сборка, архитектурный тест

- Новый пакет `internal/internalapi`: HTTP-обработчик Validate с проверкой внутреннего токена. Слушает `-internal-listen` (по умолчанию `:8081`) и запускается, только если задан токен в env `WASMHOOKS_INTERNAL_TOKEN`; тот же токен использует `HTTPSource`.
- `archtest`: `gateway` и `gateway/httpapi` не импортируют `internalapi`; `internalapi` не импортирует `gateway`.
- `dataplane/Dockerfile`: multi-stage, финальный образ distroless static, wasm-фикстуры в образ не входят.

## 9. Тестирование и CI

**Control plane** (pytest, PostgreSQL и MinIO в testcontainers):

- `bump_config_version`: конкурентные транзакции получают строго возрастающие версии в порядке коммита; снимок версии `v` содержит все изменения с версией ≤ `v` (тест на ловушку D20);
- long-poll: немедленный 200, 304 по `wait_s`, пробуждение при изменении не позже интервала опроса, 400 на некорректные параметры, 401 без токена;
- ответ снимка валиден по схеме `Snapshot` из `api/dataplane-internal.openapi.yaml`;
- golden-снимок `api/testdata/snapshot.golden.json` собирается из фиксированного набора данных и совпадает с файлом (флаг пересоздания для осознанных изменений);
- срез хуков: создание, конфликт имени, проверки схем и `sample_input`, PUT без изменений не двигает версии, PUT с изменением двигает обе, сужение `allowed_*` — 409;
- аутентификация: отозванный ключ, просроченный JWT, чужой `aud`, токен тенанта на эндпоинте оператора;
- каждая мутирующая операция сдвигает версию снимка ровно на 1.

**Data plane:** `HTTPSource` против `httptest` (200, 304, 5xx, обрыв, устаревшая версия, ошибка разбора и бэкофф); общий набор `modstore` для `FS` и `S3`; Validate на фикстурах (`discount` — ok, `http-call` — `imports`, модуль без `handle` — `exports`, `infinite-loop` — `sample_call` с `timeout`, `bad-output` — `sample_call` с нарушением схемы); `config.Parse` принимает golden-снимок; архитектурный тест с новыми правилами.

**CI:** существующие джобы без изменений плюс:

- `control-plane`: `uv sync`, `ruff format --check`, `ruff check`, `mypy`, `pytest`, проверка дрейфа `api/control-plane.openapi.yaml`;
- `e2e`: сборка образов, `docker compose up --wait`, `go test ./...` в `e2e/`, логи compose при падении.

## 11. Stretch: S7b

Набросок; детальный дизайн — в PR этой задачи.

- В executor — семафор исполняемых вызовов, захватывается непосредственно перед вызовом гостя и отпускается после. Размер по умолчанию `max(1, GOMAXPROCS − 1)`: наблюдатель отмены wazero (`CloseModuleOnCanceledOrTimeout`) — отдельная горутина на вызов, ей нужен свободный P, чтобы закрыть модуль по дедлайну.
- Доля тенанта: один тенант держит не больше `max(1, слоты / 2)` слотов, иначе тенант с зависшими скриптами занял бы все слоты и перенёс проблему на соседей в виде `unavailable`.
- Ожидание слота ограничено остатком дедлайна; не дождался — `unavailable` (скрипт не запускался).
- Повторный замер S7b на Linux (workflow `bench`) для N < ядер и N ≥ ядер; результат в `docs/spike-results.md`.

## 13. Риски

| Риск | Признак | Действие |
|---|---|---|
| Неделя не вмещает DoD | К середине недели не открыт PR1 | Уровень «желательно» переносится в M2; PR1 приоритетнее PR2, потому что разблокирует backend |
| Подводные камни async SQLAlchemy (ленивая загрузка, `MissingGreenlet`) | Падения в тестах среза | Явные запросы без ленивых связей, `expire_on_commit=False`; паттерн разобран в документе передачи |
| testcontainers на Windows и Docker Desktop | Тесты не стартуют локально | Те же тесты гарантированно идут в CI на Linux; в документе передачи — проверка Docker перед `pytest` |
| CRLF в скриптах и entrypoint контейнеров | Контейнер не стартует на Linux | `.gitattributes` уже требует LF; entrypoint без shell-скриптов, где возможно |
| Время джобы `e2e` | CI заметно дольше | Кеш слоёв Docker; джоба идёт параллельно остальным |
| Фронтенд не согласен с формами контракта | Замечания в PR1 | Формы взяты из его же моков; расхождения правятся до мержа PR1 |
| Отравленный снимок | Data plane не принимает новые версии | Ограничения БД (D22), golden-снимок, бэкофф при ошибке разбора |

## 14. Известные ограничения M1

- Последний снимок не сохраняется на диск: рестарт data plane во время отказа control plane оставляет его без конфигурации (`readyz` = 503). Кеш last-known-good на диске — MVP.
- Восстановление БД control plane из бэкапа может вернуть версию снимка назад; data plane отвергнет более старые версии до перезапуска. Решение (epoch установки в снимке) — MVP.
- JWT тенанта отзывается только истечением срока.
- Один уровень прав у ключа установки: ключ в бэкенде магазина может менять хуки.
- Квоты есть в модели и снимке, data plane их не применяет (MVP).
- Изменение схем и лимитов хука не перепроверяет привязанные модули; оператора защищает проверка выхода на горячем пути (`handler_error`).
- Без stretch S7b точность таймаутов и латентность соседей при насыщении CPU не гарантированы (спайк S7b).
