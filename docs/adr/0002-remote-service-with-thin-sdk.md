# ADR 0002: удалённый сервис плюс тонкий SDK

- Статус: принято
- Дата: 2026-09-24
- Связанные документы: основной спек §5 (решение 2), §6.1 (компоненты, SDK), §6.2 (контракты); спек M0 §4 (структура репозитория, `api/invoke.openapi.yaml`)

## Контекст

Нужно решить, где физически исполняется скрипт тенанта относительно процесса оператора: внутри процесса оператора (библиотека), рядом с ним на том же хосте/поде (sidecar), или как отдельный сетевой сервис, к которому оператор обращается через клиент. От выбора зависит, можно ли масштабировать исполнителей независимо от приложения оператора, что происходит при падении или зависании скрипта, и где живёт единая точка для квот на тенанта.

## Решение

Data plane — отдельный удалённый сервис (gateway и executor, в PoC один процесс, в MVP разные), к которому оператор обращается по сети. Поверх него — тонкий SDK: одна функция вызова хука, транспорт, дедлайн, повтор при `unavailable` до дедлайна, применение значения по умолчанию. SDK не содержит бизнес-логики: вся семантика описана на уровне HTTP API data plane (`api/invoke.openapi.yaml`), поэтому потребитель на любом языке может ходить в data plane напрямую, даже без SDK.

## Рассмотренные альтернативы

### Sidecar-процесс рядом с оператором

Плюсы: низкая латентность (localhost), нет отдельного сетевого перехода.

Минусы: не даёт независимого масштабирования — sidecar приходится масштабировать в лад с репликами приложения оператора, а не по нагрузке от исполнения скриптов; нет единого места для квот тенанта — параллельность и частота размазаны по N инстансам sidecar без координации; при разделяемых ресурсах пода зависший или прожорливый скрипт может задеть процесс оператора рядом. Отвергнута: не даёт изоляции отказов и масштабирования, которые и есть предмет проекта.

### Библиотека в процессе оператора

Плюсы: минимальная латентность, никакого сетевого перехода и отдельного развёртывания.

Минусы: рантайм и песочница должны существовать на каждом языке, на котором пишут операторы — то же дублирование PDK, от которого платформа уходит через Extism (ADR 0003), но на уровне целого исполнителя; зависший или упавший по памяти скрипт исполняется в адресном пространстве процесса оператора, а не изолированного процесса — риск уронить сам чекаут; квоты и circuit breaker пришлось бы координировать между всеми процессами оператора без единой точки. Отвергнута: ломает изоляцию отказов и мультитенантность — то, ради чего задуман проект, а не побочный эффект архитектуры.

## Последствия

### Положительные

- Независимое горизонтальное масштабирование исполнителей отдельно от масштабирования приложения оператора.
- Изоляция отказов: упавший или зависший executor не роняет процесс оператора, максимум — рост латентности одного вызова (§9 основного спека).
- Единое место квот и circuit breaker на тенанта (gateway), а не размазанная координация между инстансами.
- SDK дешёво написать на любом языке: вся семантика в HTTP API, поэтому решение 12 основного спека («Python SDK первым, Go SDK в MVP») не тормозит демо-магазин — контракт data plane это обычный HTTP, SDK тонкий.

### Отрицательные и риски

- Сетевой переход добавляет латентность к каждому вызову; митигируется бюджетом дедлайна, который передаёт SDK, и целевым SLO после спайка.
- Data plane — ещё один сервис, который оператор обязан развернуть и поддерживать (Helm-чарт, §13 основного спека) — самостоятельная эксплуатационная нагрузка, которой нет у sidecar или библиотеки.
- Нужны discovery и health-check между gateway и executor (кольцо, consistent hashing, §11.1) — сложность, ненужная в альтернативах, где gateway и executor не разделены сетью.

### Что будет означать пересмотр решения

Переход на sidecar или библиотеку означает, что SDK должен впитать всё, что сейчас живёт на сервере: не только дедлайн и повтор, но и квоты, circuit breaker, управление пулом инстансов. Это дублирует эту логику на каждом языке потребителя и снова размазывает квоты по инстансам без единой точки — то есть отменяет главный довод этого ADR. Пересмотр целесообразен, только если для одного оператора появится жёсткое требование к латентности ниже сетевого перехода, а мультитенантность внутри одной установки станет не нужна.
