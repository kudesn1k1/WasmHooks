# ADR 0001: только синхронные хуки в этом семестре

- Статус: принято
- Дата: 2026-09-24
- Связанные документы: основной спек §1, §4.3, §5 (решение 1), §7.1; спек M0 §2 («Не входит в M0»)

## Контекст

Нужно решить, какую модель вызова хука поддерживает платформа в этом семестре: только синхронную (оператор делает вызов и ждёт ответа в пределах дедлайна), только асинхронную (постановка джобы в очередь, обработка вне запроса, at-least-once, DLQ), или обе сразу. Оба сценария существуют в индустрии: Shopify Functions — синхронная модель; очереди задач с ретраями — асинхронная. Команда — три человека на семестр, включающий PoC, MVP и защиту с доказательной базой (нагрузочные тесты, отказы, живое демо).

## Решение

В этом семестре платформа поддерживает только синхронные хуки. Асинхронная модель — очереди, ретраи, DLQ, at-least-once — не проектируется детально и не реализуется даже частично, переносится в roadmap следующего семестра (спек M0 §2, список «Не входит в M0»).

## Рассмотренные альтернативы

### Асинхронная модель сразу, вместо синхронной

Плюсы: не нужно потом переучивать операторов на новую модель; подходит для тяжёлых или длительных задач.

Минусы: каждая асинхронная джоба требует очереди, DLQ, идемпотентности воркеров и отдельного наблюдения за пайплайном — сложность, которая не нужна простому случаю «посчитать скидку за 50 мс». Отвергнута: усложняет минимальный сквозной срез, который нужен для защиты уже в PoC, и не даёт быстрее показать масштабирование и отказоустойчивость — предмет курса.

### Обе модели сразу в этом семестре

Плюсы: полнота с первого дня, не нужно объяснять на защите отсутствие асинхронности.

Минусы: удваивает объём MVP — два протокола вызова, два набора тестов отказов, два вида квот на два разных пути. Отвергнута: команда из трёх человек физически не успевает, а решение 4 (эффекты как данные) показывает, что двойной путь архитектурно не нужен: асинхронность добавляется без второго протокола.

## Последствия

### Положительные

- Первый сквозной путь короче: одна модель вызова, один набор исходов (`ok`, `no_handler`, `timeout`, `handler_error`, `quota_exceeded`, `unavailable`), один контракт `api/invoke.openapi.yaml`.
- Синхронная модель — предпосылка ADR 0004 (эффекты как данные): у синхронного вызова нет промежуточного состояния «джоба поставлена, но не обработана», поэтому протоколу не нужны подтверждение старта и неоднозначные исходы.
- Async ложится сверху органично: синхронный хук в будущем возвращает эффект типа «поставить джобу» — обычный эффект из уже существующего списка типов (§6.3 основного спека), а не новый транспорт или новая семантика вызова.

### Отрицательные и риски

- Оператор с потребностью в асинхронной семантике уже сейчас (например, долгая фоновая проверка) не может использовать платформу без обхода: синхронный хук с быстрым ответом плюс эффект, обрабатываемый вне платформы.
- Требования, зависящие от очередей, архитектурно не проверяются до следующего семестра — риск, что на практике «эффект-джоба» окажется недостаточным и потребует изменения контракта `Invoke`, а не только нового типа эффекта и исполнителя эффектов.

### Что будет означать пересмотр решения

Если асинхронная модель потребуется раньше или не уложится в схему «эффект-джоба» без изменения контракта вызова, пересматривать нужно вместе с ADR 0004 — они физически связаны: у синхронного вызова нет статуса «принято, но не обработано», у асинхронного он появляется неизбежно. Пересмотр — это новая ветка протокола (не только новый тип эффекта), которая затронет `execproto`, публичный API и оба SDK.
