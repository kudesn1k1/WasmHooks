# ADR 0004: sans-IO скрипты, эффекты как данные

- Статус: принято
- Дата: 2026-09-24
- Связанные документы: основной спек §5 (решение 4, решение 5), §6.3, §7.1, §7.2, §7.3; спек M0 §3 (контекст для D8, D9 — конфиг и логи как host-функции чтения)

## Контекст

Платформа обязана уметь безопасно повторить вызов скрипта — на другом executor-е после падения узла, при обрыве соединения gateway↔executor, при перестроении кольца (§9 основного спека). Нужна модель исполнения, при которой повтор никогда не создаёт двойного эффекта в мире оператора. При этом реальные обработчики не бывают чистыми функциями входа: мерчанту может понадобиться прочитать конфиг, значение из внешнего сервиса (например, фрод-скор), логировать происходящее — а не только вычислить ответ по входу.

Команда сначала предложила модель «обработчик — чистая функция»: только вход, только выход, никаких host-функций вообще. Это было отвергнуто ещё на этапе обсуждения: обработчику нужны данные, которых нет и не может быть заранее в каждом входе (внешний фрод-скор, зависящий от конкретного входа; конфиг тенанта, который меняется независимо от вызова), а хосту нужно предоставлять функции — иначе платформа либо заставляет оператора протаскивать в каждый вызов всё, что скрипту может понадобиться, независимо от того, нужно ли это в конкретном случае, либо запрещает целый класс легитимных сценариев.

## Решение

Итоговая модель — sans-IO: чтения идут через host-функции, разрешённые оператором на конкретном хуке (сейчас — лог и конфиг; в roadmap — чтение KV, данные оператора, исходящий HTTP GET по allowlist хостов), а записи никогда не происходят внутри исполнения. Скрипт не совершает эффектов сам — он возвращает список эффектов как данные в выходе (§6.3 основного спека), а применяет их оператор (в этом семестре, вручную по коду хоста) или в roadmap — платформенный исполнитель эффектов с outbox. Поскольку внутри исполнения ничего не записывается, повтор любого вызова безопасен по построению — не нужны ни подтверждение старта, ни обработка неоднозначных исходов.

Классификация возможностей на «чтение» и «эффект» — декларация оператора на уровне хука (`allowed_host_functions`, `allowed_effect_types`), а не то, что платформа может проверить сама: платформа не способна доказать, что внешний HTTP GET по allowlist ничего не меняет на другом конце — оператор берёт на себя ответственность, классифицируя host-функцию как чтение (§7.2 основного спека).

Ключ идемпотентности передаётся оператором в `Invoke` с первого дня, хотя дедупликацию им в этом семестре никто не делает — это задел под roadmap. Каждый эффект несёт поле `key` для дедупликации применения; если скрипт его не задал, executor подставляет `<idempotency_key>:<index>`, где `index` — порядковый номер эффекта в выходе, чтобы два эффекта одного вызова не схлопнулись в один ключ.

Скрипт теряет только синхронные эффекты изнутри исполнения — он не может сам, прямо во время вызова, записать что-то в БД оператора или дёрнуть платный вебхук. Доступа к данным он не теряет: всё, что оператор готов предоставить, доступно через host-функции чтения, а желаемое изменение мира скрипт всё равно может выразить — просто как данные в ответе, а не как немедленное действие.

Индустриальный прецедент: Shopify Functions — та же форма решения одной и той же проблемы (безопасный по повтору sandboxed-обработчик, который возвращает данные вместо того, чтобы действовать).

## Рассмотренные альтернативы

### «Обработчик — чистая функция» (без host-функций вообще)

Плюсы: максимально простой протокол, тривиально безопасен по повтору, минимальная поверхность атаки — вообще никаких host-функций.

Минусы: не соответствует тому, что нужно реальным обработчикам. Данные вроде внешнего фрод-скора или актуального конфига тенанта нельзя надёжно протащить заранее в каждый вход: либо оператор обязан заранее вычислять и передавать всё, что скрипту может когда-либо понадобиться, независимо от того, использует ли скрипт это в конкретном вызове (расточительно и не масштабируется на будущие непредвиденные потребности), либо платформа отказывает в легитимном классе сценариев целиком. Отвергнута не потому, что небезопасна, а потому что не решает задачу, для которой обработчики вообще пишутся.

### Симметричные host-функции чтения и записи

Плюсы: эргономически проще для автора скрипта — нет отдельного понятия «эффект», просто вызов функции делает то, что нужно, как в обычной библиотеке.

Минусы: host-функция записи совершает эффект синхронно прямо внутри исполнения, а платформа рутинно повторяет вызовы (перестроение кольца, повтор gateway при обрыве соединения) — повтор такого вызова выполнил бы запись дважды, и платформа не может ни узнать об этом, ни предотвратить. Это напрямую ломает решение 4 основного спека («скрипт чистый по построению») и возвращает ровно те проблемы — подтверждение старта, неоднозначные исходы, — которых модель сознательно избегает. Отвергнута.

## Последствия

### Положительные

- Повтор вызова безопасен всегда — основа изоляции отказов: перестроение кольца, повтор gateway, восстановление после падения executor-а не требуют дополнительной защиты от двойного применения на уровне протокола вызова.
- Скрипт не деградирует до «чистой функции»: он сохраняет доступ к данным через host-функции чтения, разрешённые оператором, — реальные сценарии (фрод-скор, конфиг, лог) продолжают работать.
- Ключ идемпотентности уже в контракте `Invoke` и в ключах эффектов — платформенный исполнитель эффектов с outbox (roadmap) добавляется аддитивно, без изменения контракта вызова.
- Классификация декларативна и находится в одном месте (хук), а не разбросана по коду — оператор один раз решает, что «чтение», а что «эффект».

### Отрицательные и риски

- Применяет эффекты в этом семестре оператор, а не платформа: если код оператора, применяющий эффект, содержит баг, платформа не видит и не может повторить это применение — гарантия «повтор безопасен» относится к вызову скрипта, а не к шагу оператора после него.
- Граница «чтение» держится на декларации оператора, а не на проверке платформой: оператор может по ошибке объявить читающей host-функцию, у которой на самом деле есть побочный эффект на другом конце (например, HTTP GET, вызывающий вебхук) — платформа этого не поймает.
- Декларативное описание потребностей скрипта в данных (по образцу input query в Shopify Functions) ещё не спроектировано; до его появления в roadmap каждая новая потребность в чтении — это ещё одна host-функция, добавленная по необходимости, что может разрастись в громоздкую поверхность API хука.

### Что будет означать пересмотр решения

Разрешить host-функциям запись внутри исполнения означало бы вернуть в протокол подтверждение старта и обработку неоднозначных исходов — то есть отменить именно то, что дало ADR 0001 (только синхронные хуки) и это решение вместе. Это более крупный редизайн, чем замена рантайма: он затронет `execproto`, публичный API и каждый путь повтора в gateway и executor-е (§8, §9 основного спека), а не только одну host-функцию.
