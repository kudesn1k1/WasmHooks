# web

Фронтенд WasmHooks: консоль оператора, консоль тенанта и витрина демо-магазина (Next.js, route groups `(operator)`, `(tenant)`, `(storefront)`).

- Владелец: frontend (см. `docs/TEAM.md`).
- Потребляет: `api/control-plane.openapi.yaml` (консоли), `api/demo-shop.openapi.yaml` (витрина). В data plane не ходит никогда.
- Моки API (MSW) по контрактам из `api/`: для тестов, для работы без docker и для эндпоинтов, которых ещё нет на бэкенде.
- Задачи Milestone 1 и точки синхронизации с backend: `docs/handoff/frontend.md`.

## Запуск

Нужен Node.js 22 или новее.

```bash
cd web
npm install
npm run dev        # http://localhost:3000
```

По умолчанию консоли ходят в настоящий control plane на `http://localhost:8000`, его поднимает `docker compose up` из корня репозитория. Без docker можно запустить всё на моках: `NEXT_PUBLIC_API_MOCKING=all` в `.env.local` (см. ниже).

| Адрес | Что это |
|---|---|
| `/`, `/cart` | витрина демо-магазина |
| `/tenant#token=<jwt>` | вход в консоль тенанта по ссылке из магазина |
| `/tenant/hooks` | консоль тенанта: хуки, загрузка и проверка модуля, активация и откат версии, параметры скрипта (конфиг привязки) |
| `/tenant/invocations` | лог вызовов: только на моках, в меню скрыт до MVP |
| `/operator/hooks` | консоль оператора: вход по ключу установки, список, создание и редактирование хуков |
| `/operator/tenants` | консоль оператора: тенанты и квоты, вход в консоль тенанта |
| `/operator/api-keys` | консоль оператора: выпуск и отзыв ключей установки |

Проверки, те же, что в CI:

```bash
npm run typecheck
npm run lint
npm test
npm run build
```

## Моки API и прокси

Браузер ходит только на свой origin, в `/api/v1/*`. Next.js проксирует эти запросы в control plane: rewrite в `next.config.ts` ведёт на `${CONTROL_PLANE_URL}/api/v1/*`. По умолчанию `CONTROL_PLANE_URL` равен `http://localhost:8000`. CORS поэтому не нужен. Rewrites читаются при сборке, так что для `next build` переменная нужна уже на этапе сборки.

Перед прокси запросы может перехватить MSW (`src/mocks`). Режим задаётся в `.env.local` переменной `NEXT_PUBLIC_API_MOCKING`:

| Режим | Что делает |
|---|---|
| `disabled` (по умолчанию) | моков нет, всё идёт в control plane |
| `partial` | моки отвечают только за эндпоинты, которых ещё нет в API (сейчас это лог вызовов); остальное уходит через прокси в control plane |
| `all` | отвечают все моки, бэкенд не нужен |

В продакшен-сборке моки выключены всегда.

Что ещё не реализовано на бэкенде, перечислено в одном месте: `src/mocks/pending.ts`. Там осталась только группа `invocations`, она остаётся до MVP.

Пример `.env.local` для работы без docker:

```
NEXT_PUBLIC_API_MOCKING=all
```

Модуль на настоящем бэкенде проверяет data plane из `docker compose`, проверка занимает пару секунд. Если data plane недоступен, версия остаётся в статусе «Проверяется». Для ручной проверки подходят файлы из `dataplane/testdata/wasm/`: `discount.wasm` проходит проверку, `http-call.wasm` отклоняется на `imports`.

Моки ведут себя как настоящий API:

- без заголовка `Authorization` отвечают `401` «Не авторизован» с `WWW-Authenticate: Bearer`; в режиме `all` подходит любой непустой токен;
- данные: тенанты `merchant-a` и `merchant-b`, два ключа установки (один отозван), консоль тенанта `merchant-a` с хуками `checkout.discount` и `order.validate`; состояние живёт в памяти вкладки;
- токен отозванного ключа получает `401`, как на настоящем бэкенде; `console-sessions` выдаёт неподписанный JWT с `sub` тенанта;
- загрузка больше 10 МиБ получает `413`, пустой файл — `422`;
- загруженная версия около 3 с проверяется, потом становится `validated`; если в имени файла есть `http`, она отклоняется с причиной из проверки `imports`;
- в лог вызовов каждые несколько секунд добавляются новые записи.

Тесты (Vitest) используют все обработчики через `msw/node`.

### Токены консолей

`apiRequest` сам подставляет `Authorization: Bearer <токен>`: на `/api/v1/tenant/*` идёт токен тенанта, на остальные пути — ключ установки. Оба токена хранятся только в `sessionStorage`. Ответ `401` стирает токен той консоли, которой он пришёл, и консоль снова показывает экран входа. Ответ `501` показывается как «Ещё не реализовано на бэкенде: T…».

Консоль тенанта открывается ссылкой `/tenant#token=<jwt>`: токен из фрагмента сохраняется, а сам фрагмент сразу убирается из адреса. Фрагмент не уходит на сервер и не попадает в логи и `Referer`. В шапке видны тенант (`sub`) и время окончания сессии (`exp`). Подпись на клиенте не проверяется, это делает сервер. Когда наступает `exp`, консоль сама показывает экран истёкшей сессии. На этом экране токен можно вставить руками, а в `npm run dev` там же есть подсказка, как его получить. В режиме `all` подходит `/tenant#token=mock`.

Токен от control plane:

```bash
curl -s -X POST localhost:8000/api/v1/tenants/merchant-a/console-sessions -H "Authorization: Bearer $KEY"
```

### API консоли тенанта

Контракт — `api/control-plane.openapi.yaml`, он генерируется из кода control plane. Моки повторяют его формы, схемы ответов описаны в `src/entities/*/model/schema.ts`. Поля, которые в контракте `nullable` или необязательны, схемы принимают и как `null`, и как отсутствующие (`.nullish()`). Тенант определяется токеном консоли, поэтому его id в путях нет. Ошибки приходят в формате RFC 9457 (`application/problem+json`).

Лог вызовов `GET /api/v1/tenant/invocations?outcome=&hook=&limit=` (`{ items: Invocation[] }`, новые сверху) в контракт не входит до MVP и есть только в моках.

### Типы из контракта

`npm run api:types` генерирует `src/shared/api/contract.gen.ts` из `api/control-plane.openapi.yaml`. Сгенерированный файл лежит в репозитории, руками его не правят. После изменения контракта команду нужно запустить заново и закоммитить результат: CI генерирует файл сам и падает, если он отличается от закоммиченного.

Zod-схемы сверяются с контрактом в файлах `src/entities/*/model/contract.check.ts` и `src/shared/api/contract.check.ts`. Это только типы, их проверяет `npm run typecheck`:

- `AcceptsContract<typeof schema, ContractSchema<"Имя">>` — всё, что разрешает контракт, проходит схему ответа (`z.input`);
- `FitsContract<Тип, ContractSchema<"Имя">>` — тело запроса, которое отправляет фронтенд, подходит под контракт.

Если бэкенд, например, сделал поле `nullable`, а схема ждёт только строку, `tsc` падает на строке этой схемы.

## Стек

Next.js 15 (App Router), TypeScript (strict), Tailwind CSS 4 и shadcn/ui (Radix), TanStack Query, Zod (проверка ответов API), MSW, Vitest и React Testing Library. React Hook Form, Zustand, Recharts и Playwright подключаются вместе с первыми экранами, которым они нужны.

## Структура

Feature-Sliced Design, адаптированный под App Router:

```
src/
  app/          роутинг Next.js и слой app из FSD: layout-ы, провайдеры (_providers)
    (storefront)/  (tenant)/  (operator)/   route groups со своими layout-ами
  views/        страницы (слой pages из FSD; имя pages в Next.js зарезервировано)
  widgets/      крупные блоки: оболочка консоли, шапка витрины
  features/     действия пользователя: загрузка модуля, активация версии
  entities/     сущности предметной области: хук, модуль, тенант, вызов
  shared/       ui (shadcn), lib, config, api
mocks/          MSW-обработчики и данные; вне слоёв FSD, только для dev и тестов
```

Слой импортирует только слои ниже себя. Слайс наружу отдаёт только то, что экспортирует его `index.ts`. Файлы в `src/app/**/page.tsx` тонкие: они только подключают страницу из `views`.

## shadcn/ui

Конфигурация лежит в `components.json`, компоненты — в `src/shared/ui`. Новый компонент добавляется командой `npx shadcn@latest add <имя>`. Реестр `ui.shadcn.com` доступен не из всех сетей: если команда падает по таймауту, нужен VPN.
